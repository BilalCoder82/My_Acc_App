# PHASE 3B-5-C — Historical Cost Correction: Discovery + Design Questions
No code in this document. No decision is made here that belongs to you/the business — each open question below is presented with options and tradeoffs, not a chosen answer. Where a question has an obvious constraint from 3B-5-A/B, that constraint is stated as a hard boundary, not a design choice.

## Hard constraints carried over from 3B-5-A/B (not open questions — already proven)
1. `InventoryMovement` is append-only; no design here may introduce in-place mutation of a historical row.
2. A POSTED `JournalEntry`/invoice line is never edited in place — any accounting effect of a correction must go through the existing Boundary (`post_immediate`/`reverse`), the same as every other posting path.
3. Warehouse isolation must be preserved — a correction to Item X/Warehouse A must not touch Item X/Warehouse B.
4. OUT movements are valued at their own stored `unit_cost` — if a correction changes that value, it is changing a historical fact, which is a much bigger claim than "recomputing an average"; this needs to be named explicitly as a decision point (see Q1), not assumed away.
5. `accumulate_average_cost()` is agnostic to input order — whatever ordering Q-Ordering below settles on, the arithmetic itself doesn't need to change.

## Are Finding A and Finding D actually the same problem?
Explicitly not assumed to be. What they share and where they diverge:

| | Finding A (backdated purchase → sale COGS) | Finding D (backdated transfer) |
|---|---|---|
| Has a JournalEntry involved? | Yes — COGS/Inventory accounting effect | **No** — `transfer_stock()` creates zero accounting entries |
| Downstream effect if recalculated | COGS on a POSTED sale, possibly cascading to more sales | Only the transfer's own `unit_cost`, and whatever the destination warehouse's own average is built from afterward |
| Correction touches accounting? | Yes, potentially | No — inventory quantity/value only |
| Correction touches POSTED immutability? | Yes, directly | Indirectly — no JournalEntry to protect, only movement values |

**This matters for scope**: a mechanism heavy enough to handle Finding A (accounting corrections, POSTED-safety) may be unnecessary machinery for Finding D, which might be resolvable with a lighter-weight "re-price this movement" operation since no journal entry exists to protect. Recommend treating them as two **separate correction executions**, each consuming shared **infrastructure/domain-calculation primitives** (chronological ordering, impact analysis) — not a shared correction *workflow*:

```
chronological movement ordering
        ↓
impact analysis
        ↓
A-specific correction execution      D-specific transfer costing correction
```

The shared part is calculation infrastructure; the correction workflow itself (what gets created, what accounting effect follows, what "done" means) stays fully separate per finding. A single `HistoricalCorrectionService` sized for A's complexity and reused for D would be over-abstraction driven by name similarity, not by shared responsibility.

## Q1 — What does "historical correction" mean, precisely?
Three structurally different options, not variants of the same thing:
- **(a) Historical Cost Reconciliation / Simulation** (renamed from "recompute-and-report" — this is not Historical Correction in the full sense, and calling it that would blur the terminology later): show the user what the "correct" average/COGS would now be, without touching any posted data. No accounting entries. Purely informational (e.g., a reconciliation report). Lowest risk, lowest value.
- **(b) Additive correction entries**: leave the original POSTED sale/COGS untouched; post a *new*, separate correction journal entry for the delta. **This option cannot be chosen yet as stated** — it presupposes a defined "Correction Event," which does not yet exist as a concept. Concretely: if Sale A's COGS moves from 100 to 120 (Δ+20), and that same average-cost shift cascades into Sale B's COGS moving from 150 to 170 (Δ+20), what is *one* correction event — one entry per document, one per date, one per account, one lump-sum entry for the whole chain, dated at correction time or at each original document's date? Each answer produces a different, auditable accounting outcome. (b) is not adoptable until a Correction Event is defined (see Q3).
- **(c) Blocked-until-resolved**: reject the backdated insert outright if it would invalidate an already-POSTED downstream calculation, forcing the user to handle it via manual adjustment instead of automatic correction. Simplest to build, but may be unacceptable if backdated entries are a normal part of the accountant's workflow (worth asking: how often does this actually happen in practice for this business?).

These are not mutually exclusive across scenarios — e.g., (c) below a chain-size threshold, (b) above it, is itself a legitimate design, but that combination should be a conscious choice, not a default.

## Q1 — REVISED: three-tier structure (supersedes the flat a/b/c framing above)
The a/b/c framing above conflated three genuinely different layers of authority into one choice. Revised structure, three separate tiers, in order:

1. **Recalculation / Simulation** — "if we rebuilt historical cost state, what would the result be?" No data changes, nothing persisted, purely computational (this is what "(a)" above actually described).
2. **Correction Event** — the system has detected a specific historical discrepancy and retains a reviewable, persisted record of it. Creating this record does **not** imply a journal entry was or will be created — it is a discovered-and-recorded fact about a discrepancy, not an accounting action.
3. **Accounting Correction** — a Correction Event has been approved and converted into an actual accounting effect via the existing Boundary (`post_immediate`/`reverse`) — original POSTED facts remain untouched throughout, per the principle already established above.

A Correction Event's exact required contents are deferred to the Correction Event definition, but must include (at minimum, as **structural attributes** — not yet a decided schema/column/enum): what triggered it, what date/period it represents, which documents it covers, whether it represents a single delta or a chain of deltas, what original facts it's based on, what derived state it computed, the before/after impact, and the `chronology_basis` (known vs. assumed) established in Q2.5 above — as a first-class part of the event's identity, not a report-time annotation.

**Two sub-questions surfaced by this structure, not yet answered:**
- **Event creation trigger — eager or lazy?** Is a Correction Event detected and created automatically the moment a backdated movement is inserted (eager — but this couples ordinary posting to potentially expensive impact analysis, colliding with the Q2.5/Q5 performance concerns), or only when explicitly requested by the accountant for a given item/period (lazy — cheaper, but historical discrepancies can sit undetected indefinitely until someone asks)? This determines *when* everything below even runs, not just what it produces.
- **Pending-event staleness.** Any tier gated on human approval (see the governing question below) creates a time gap between detection and decision. If new movements are entered during that gap that would change the Correction Event's own analysis, does the pending event become invalid and require re-analysis, or can it be approved as originally computed regardless of what's changed since? Undefined today; needs an explicit answer as part of the Correction Event's own lifecycle, not left implicit.

## Governing question for Q1: does chronology confidence gate the authority to move between tiers?
Not decided — three candidate policies, presented for evaluation, none adopted:
- **Policy A (Conservative)**: `known` chronology may proceed to Accounting Correction; `assumed` chronology is capped at Recalculation/Simulation unless the accountant explicitly promotes it.
- **Policy B (Permissive)**: even `assumed` chronology may reach Accounting Correction automatically if other conditions are met. Higher accounting risk — a posted entry could rest on an unproven ordering assumption.
- **Policy C (Hybrid)**: `assumed` chronology may reach a fully-prepared Correction Event, including a proposed journal entry, reason, chronology basis, affected movements, before/after, ΔInventory, ΔCOGS — but never auto-posts. The accountant reviews and explicitly approves before it becomes an Accounting Correction.

No policy is adopted here. Policy C is noted as attractive for this specific business (high same-date transaction volume across three restaurant concepts means a purely conservative policy could leave most real discrepancies stuck at simulation-only, while a permissive policy risks posting on unproven assumptions) — but this is an observation to weigh, not a decision made on the business's behalf.

## DECIDED — Correction Event lifecycle, creation policy, and chronology-confidence policy

**Lifecycle:**
```
Candidate → Analysis → Pending/Proposed → Approved → Accounting Correction
                              ↓
                            Stale → Re-analysis
```
`Stale` is not a failure or a historical cancellation — it means the analysis behind a Pending event no longer reflects the current data and cannot be approved as-is; it must be re-analyzed before it can move forward again.

**Creation policy — Lazy with a lightweight detection hook** (not full Eager, not pure Lazy):
- At ordinary posting time, a cheap check runs: "could this backdated movement possibly affect an existing historical cost state?" (e.g., does any movement for this item/warehouse already exist dated after this one — a single indexed existence check, not a full recompute). If so, a **Candidate** is recorded — nothing more.
- Full Impact Analysis (Q2/Q2.5) only runs when the accountant explicitly requests "Analyze / Reconcile Historical Cost" for that candidate (or item/period). This keeps ordinary posting cheap and decoupled from correction workload, consistent with the existing performance-trigger discussion (Q5/Q7).
- **Not yet addressed and flagged now**: this detection hook must fire for **both** Finding A (purchase/sale chains) and Finding D (stock transfer backdating) — the "cost state" the hook checks for must not be scoped only to purchase/sale movements by default, or Finding D will quietly fall outside the lifecycle being designed for Finding A. This needs explicit confirmation when the hook is actually specified, not assumed here.

**Snapshot validity / staleness principle:**
> A pending Correction Event becomes stale when a subsequent data change may affect the factual/derived state on which that Event's analysis depends — not on any unrelated data change in the system.

Each Correction Event represents an analysis of a specific data state (an "Analysis Snapshot / Data Revision" concept — its concrete form, whether a revision number, sequence, timestamp, or hash, is deferred; only the concept is fixed now). Staleness is scoped by **Impact Scope**, which is not yet defined — that definition depends on Q2's answer (propagation/scope of the recalculation chain), so this principle is stated now but cannot be fully operationalized until Q2 is resolved. This is itself the reason for the resolution order below.

**Flagged concern, not resolved**: Q2's current framing rejects quantity-convergence as a stopping rule in favor of "propagation continues while a cost-state difference persists" — which, left unbounded, could mean propagation (and therefore the staleness-triggering range) extends indefinitely forward toward "now" for an actively-moving item. If so, in a business with the transaction volume described here, a Pending Correction Event for a fast-moving item could go stale within minutes of creation, every time — before an accountant realistically has a chance to review and approve it. If this turns out to be the case once Q2 is resolved, "Pending Approval" as a workable human-in-the-loop state may need a bounded-scope answer to Q2 specifically to remain usable in practice, not just a theoretically correct unbounded one. This is a dependency Q2's design should weigh explicitly, not discover after the lifecycle above is built.

**Chronology-confidence policy — Policy C adopted (Hybrid)**:
- `known` chronology → may proceed through the full lifecycle up to Accounting Correction (subject to whatever approval policy Q1/Q5 ultimately requires — this does not itself mean automatic posting).
- `assumed` chronology → may reach a fully-prepared Pending Correction Event (reason, chronology basis, affected movements, before/after, ΔInventory, ΔCOGS, proposed entry) but **never auto-posts**; requires explicit accountant approval to become an Accounting Correction.
- Governing rule: **the more assumption involved, the less automatic authority the system has to create an accounting effect.**

## Recommended resolution order for remaining questions
Q1 (lifecycle + policy — now decided above) → **Q2** (propagation/impact-scope definition) → **Q2.5** (ambiguity/tie resolution) → **Q3** (Correction Event's concrete fields/schema). Q3 is deliberately last: designing Correction Event's structure before Q2 defines what "impact scope" even means would mean designing a schema for a concept that doesn't have a definition yet.

## Q2 — Cost-State Propagation and Impact Scope (rebuilt from first principles, not "how many movements do we recompute")
The real question: after a new historical movement is inserted, what is the smallest set of future movements that must be re-evaluated before we can prove the historical difference no longer has effect?

Two prior candidate stopping rules are both explicitly rejected, for different reasons:
- **Quantity convergence** ("stop once quantity returns to its pre-correction value") — already rejected: quantity and cost are different state dimensions. Example: Opening 100@10 → Sale 50@10 → Purchase 50@20 → Sale 50@20. Quantity can return to a "looks unaffected" state while COGS on the second sale still differs from its pre-correction value.
- **Unconditional recompute to "now"** — not rejected outright (it may be the correct answer in some cases), but not adopted as a default either: doing this unconditionally risks making Pending Events impractical in an actively-moving business before we've established it's actually necessary.

**Framing: compare two states, not a single recomputed number.**
- **Baseline state** — what the system would have reached without the new historical movement.
- **Recalculated state** — what it reaches with that movement correctly placed at its economic position.

For each movement downstream of the insertion point, the comparison must track a **state vector** — see Q2.1 below for its candidate composition, not a single value. A correction continues to propagate for as long as *any* component of that vector still differs between Baseline and Recalculated for some movement not yet examined.

**This question is now answered — see Q2.3 below: DISPROVEN.** State-vector matching at some movement does *not* guarantee everything after it is unaffected; cost differences can and do reappear later even after an apparent local match. This was established by direct proof (not just empirical search) and verified computationally. It determines that "stop early on a local match" is never safe in the general case — see Q2.3 for the proof and its consequence for Q2.7.

**Sub-questions, addressed one at a time as Q2.1, Q2.2, ... — not all answered here:**

### Q2.1 — What is the state vector? — CANDIDATE (composition still open; **sufficiency-as-a-stopping-test is now moot — see Q2.3's result below: no local test on any vector is a valid stopping rule**)
Split into two levels, not one combined vector — because `InventoryMovement` represents an inventory fact, while COGS is an *accounting effect derived from* that fact, and conflating them would blur exactly the distinction Q3 needs later between Correction Event (a discovered fact difference) and Accounting Correction (its accounting consequence):

- **A. Inventory Cost State** (per movement, after it's applied): `quantity_on_hand`, `inventory_value` (at weighted-average cost), `average_cost` (`inventory_value / quantity_on_hand`, with the existing zero-quantity handling from `accumulate_average_cost()` applying unchanged).
- **B. Movement Cost Effect** (per movement): `movement_unit_cost` — for IN, the cost assigned to that movement; for OUT, **the historically stored fact** `InventoryMovement.unit_cost` itself, not a re-derivable value — and `cogs_consequence` — for a Sale OUT, `quantity × movement_unit_cost`, tagged conceptually as a `CostAccountingEffect` rather than as inventory state proper.

Comparison is always Baseline vs. Recalculated across both levels. **Explicit principles governing this candidate vector:**
1. `movement_unit_cost` on an OUT movement is treated as a historical stored fact for comparison purposes, not a value that gets silently recomputed.
2. `cogs_consequence`/`CostAccountingEffect` is a derived accounting effect, not part of inventory state itself — this separation matters directly for how Correction Event vs. Accounting Correction get defined in Q3.
3. **No single component's match (e.g., `average_cost` alone) may be assumed sufficient to prove propagation has ended.** A later movement can match on `average_cost` while still differing on `movement_unit_cost` or `cogs_consequence`, or vice versa.
4. **Whether this five-field candidate vector is even sufficient to prove no future effect exists is not established here — that is Q2.3's job, not an assumption of Q2.1.** This vector may need revision once Q2.3 is examined.

### Q2.2 — Affected Movement Definition — CANDIDATE (detection/classification only, not a stopping rule)
A single naive test ("did `average_cost` change?") is insufficient — an accounting-relevant difference can surface even when other components look unaffected. Three layers, all independent, any one of which is sufficient to mark a movement Affected:

- **Layer A — Cost State difference**: `quantity_on_hand`, `inventory_value`, or `average_cost` differs between Baseline and Recalculated.
- **Layer B — Movement Cost difference**: `movement_unit_cost` differs — critical for OUT movements specifically, since the stored `InventoryMovement.unit_cost` is a **historical fact**, and what a chronological recalculation *would* produce is a separate, comparison-only value. If `stored unit_cost != recalculated unit_cost`, the movement is Affected regardless of what the system later decides to do about it — detecting the discrepancy is not the same act as authorizing a change to the stored fact (the principle already established above: recalculation detects, it does not mutate).
- **Layer C — Accounting Effect difference**: the derived effect (e.g., COGS for a Sale OUT) differs between Baseline and Recalculated. This is intentionally kept separate from Layer A per the Q2.1 split (Inventory Cost State ≠ Accounting Effect) — a cost-state difference does not automatically imply an accounting-effect difference, and the reverse must not be assumed either.

**Formal candidate definition:**
```
Affected(M) =
      CostStateBaseline(M)      != CostStateRecalculated(M)
   OR MovementCostBaseline(M)   != MovementCostRecalculated(M)
   OR AccountingEffectBaseline(M) != AccountingEffectRecalculated(M)
```

**Caution — not naive per-field inequality.** Some fields are derived from others (`average_cost = inventory_value / quantity`), so a single root cause can surface as multiple apparent differences. Q2.2 only answers *whether* a movement is Affected (**Detection**); it is not responsible for *what kind* of difference it is (**Classification**) or *what follows from it* (**Impact**) — collapsing these would risk a Correction Event reporting "7 differences" when the economic reality is "1 backdated purchase → revalued inventory → 3 downstream sales changed." Classification and Impact are separate work for later in the design, not resolved by this definition.

**Worked example** (illustrating Affected without yet answering whether propagation can stop):
- Baseline: T1 Purchase 100@10 (qty 100, value 1000, avg 10) → T2 Sale 20 (qty 80, value 800, avg 10, OUT cost 10, COGS 200).
- A backdated T0 Purchase 100@20 is inserted. Recalculated: T0 (qty 100, value 2000, avg 20) → T1 (qty 200, value 3000, avg 15) → T2 (qty 180, value 2700, avg 15, OUT cost 15, COGS 300).
- T0, T1, T2 are all Affected; T2 additionally carries a $100 accounting-effect difference (COGS 200→300).
- Suppose some later movement shows Baseline and Recalculated fully matching again (e.g., qty 100, value 1500, avg 15 on both sides). **This does not yet mean propagation stops here** — that determination belongs entirely to Q2.3, not to this definition. Q2.2 only says whether a given movement is Affected; it makes no claim about what a later match implies for movements beyond it.

**Explicit non-implications, to prevent this definition from being read as more than it is:**
- Affected is a detection/classification concept — it does not itself decide that an Accounting Correction is required.
- Affected does not mean the original stored record will be modified (Layer B specifically depends on this holding for OUT movements).
- Multiple Affected components do not imply multiple independent economic causes (see the derived-field caution above).
- This definition does not determine where propagation ends — deferred entirely to Q2.3.
- Chain size or movement count plays no role in this definition — that belongs to Q2.7/Q5, not here.

### Q2.3 — Propagation Termination / Convergence — **DISPROVEN** (established by direct proof, verified computationally, not merely by search)

**Verdict: no local/pointwise convergence test — neither full state (Q,V) nor average cost alone — can be relied on as a safe early-stopping rule.** This is a negative mathematical result, not an unresolved question; it changes what Q2.7 is allowed to attempt.

**Lemma 1 (quantity offset is a permanent invariant).** In the pure-insertion model (Recalculated = Baseline's original movement sequence plus exactly one additional backdated IN, with every other movement's own parameters unchanged), `Q_recalculated(i) − Q_baseline(i)` equals the backdated movement's own quantity for every subsequent movement `i`, with no exception — because every later IN or OUT applies an identical quantity delta to both branches, preserving a constant difference exactly. Verified computationally across a multi-step sequence (offset stayed exactly 10 across 4 subsequent movements of mixed IN/OUT). **Direct consequence: the full state (Q,V) can never exactly re-match after divergence unless the backdated quantity is itself zero** — "wait for the full state to match again" is not merely unsafe as a stopping rule, it is typically *unreachable* in the first place.

**Lemma 2 (OUT never changes average cost).** Because an OUT movement removes stock priced at exactly the current average, the average of what remains is algebraically unchanged (`(AQ − qA)/(Q−q) = A`). Verified computationally (before = after = 15, exact). Consequence: divergence between the two branches' average cost can only be introduced or removed by an **IN** movement — OUT movements are neutral to it.

**Disproof (constructed, then computationally verified).** Since full-state matching is essentially unreachable (Lemma 1), the only remaining candidate for a "local match" worth testing is average cost alone. A matching average cost was deliberately engineered at a point where Q, V still differ (Baseline: Q=90, avg=10; Recalculated: Q=100, avg=10 — same average, permanently different quantity, per Lemma 1). The identical next IN movement (qty=10, cost=20) was then applied to both branches. Result: `avg_baseline → 11`, `avg_recalculated → 10.9090...` — **the match breaks immediately**, because the same purchase quantity dilutes two permanently different base quantities by different proportions. This is not an edge case requiring rare conditions — it is the generic behavior of the dilution formula whenever the two branches' quantities differ at all, which Lemma 1 establishes is always the case after any nonzero backdated insertion.

**What this rules out, and what it does not:**
- Ruled out: any design that attempts to terminate propagation early because some downstream movement's state (fully, or on average cost alone) happens to match between Baseline and Recalculated. Such a match provides no guarantee about anything after it.
- Not addressed by this result: what happens under models more complex than "a single pure additive insertion" (e.g., a backdated *edit* rather than insertion, multiple concurrent historical corrections, or Finding D's cross-warehouse transfers) — this proof's scope is the single-insertion case central to Finding A; extending it is explicitly Q2.4's job (Finding D) and a caution for Q3 (Correction Event definition) if multiple corrections can be pending concurrently in overlapping ranges.
- Not addressed: rounding/quantization was not needed to produce this counterexample (it holds in exact arithmetic) — meaning the actual system's Decimal rounding can only make convergence *less* likely to persist, never provide a rescue.

**Consequence for Q2.7 (Scope Bounding):** because no mathematically valid early-termination test exists, Q2.7 is not a fallback for unusually large chains — it is now the *only* mechanism available to make propagation analysis tractable at all, short of full recomputation to "now" in every case. The choice becomes explicit: (a) always recompute forward to the present state (correct, but potentially expensive per the existing performance-trigger discussion), or (b) adopt an accepted engineering/business bound, explicitly documented as a *policy decision*, not a discovered mathematical safe point. There is no third option where a clever local check quietly makes this cheaper for free.

### Q2.4 — Finding D Propagation Across Warehouses — **ANSWERED** (four lemmas + one isolation test, all constructed and computationally verified, not assumed from Q2.3)

**Method note:** the "Recalculated" branch here models a *counterfactual* point-in-time transfer costing (transfer cost = source warehouse's average at the transfer's correct chronological position) — distinct from the actual implementation's current behavior (Finding D itself: cost = source average *at call time*). This is deliberate: to learn how far a correction *would* propagate under correct point-in-time costing, independent of whether the system currently computes it that way.

**D-Lemma 1 (quantity invariant, same mechanism as Finding A) — CONFIRMED.** Inserting an *additional* backdated Transfer(W1→W2, qty=T) produces a permanent quantity offset of exactly `−T` in the source and `+T` in the destination, constant across every subsequent event in both warehouses (verified: `-10` and `+10` held exactly across 5–6 subsequent steps). Same structural cause as Q2.3's Lemma 1 (identical subsequent deltas applied to both branches), now confirmed to hold independently in *each* warehouse's own quantity ledger.

**D-Lemma 2 (source average is affected) — CONFIRMED.** A backdated purchase in W1, entered before an *existing* transfer, changes W1's average at the transfer's point (verified: 10 → 14.2857...) — this is exactly Q2.3's single-warehouse result, unsurprising on its own.

**D-Lemma 3 (destination average is affected, but through a structurally different mechanism than Finding A) — CONFIRMED, with an important refinement.** Because the transfer's own *quantity* is unchanged between branches (only its *cost* differs, since W1's average changed), the destination warehouse's quantity trajectory is **identical in both branches at every step** (verified: `True` at every checkpoint) — unlike Finding A's permanent quantity offset, this is a **value-only offset with matching quantities**. Two further, newly-discovered sub-properties of this value-offset case (verified numerically, not previously claimed anywhere in this document):
- A subsequent OUT in the destination **exactly preserves** the average-cost difference (verified: 8.5714... before and after the destination's OUT — unchanged to the full precision shown). This follows algebraically: if quantities match exactly between branches, `avg_diff = ΔV/Q` is unaffected by OUT, since both branches' `V` and `Q` shrink by the same proportion (see the `(Q−q)/Q` cancellation in the underlying dilution formula).
- **A subsequent IN in the destination is expected to *dilute* (shrink, not eliminate) that difference asymptotically, per the same dilution algebra as Q2.3 — but this specific sub-claim was not itself numerically re-verified in this exploration (only the OUT-preserves case above was).** It is not recorded as a proven lemma — only as a hypothesis consistent with the algebra, to be verified separately (mirroring the analytical-then-computational standard already applied in Q2.3) before it is relied on.
- **Consequence: this is a materially different (milder, monotonically non-increasing rather than potentially re-diverging) propagation shape than Finding A's — but still never guaranteed to reach exact zero difference in finite time except by coincidence.** It must not be assumed to inherit Q2.3's exact disproof mechanism, nor assumed to be "safer" without this distinction being stated explicitly, which is why it's recorded here rather than left implicit.

**Independent discovery this forces: two distinct propagation paths exist, not one.** Finding A propagates via a permanent *quantity* displacement (`ΔQ ≠ 0`, constant, per Q2.3's Lemma 1). Finding D's destination-side propagation, as just shown, involves `ΔQ = 0` with `ΔV ≠ 0` instead. Quantity mismatch is therefore **not a necessary condition** for ongoing historical-cost propagation — a warehouse can carry a real, undiscovered cost discrepancy while its quantity ledger matches the baseline exactly. Concretely: `A: historical change → quantity/state displacement → downstream effects`, while `D: historical change → transfer cost/value difference → downstream cost-state effects`. This is a second, independent reason Q2.7 cannot be built around a single invariant like "does quantity differ" — that test would silently miss Finding D's destination-side propagation entirely.

**Isolation test (dependency chain confirmed exactly as hypothesized) — CONFIRMED.** Case A (backdated purchase entered chronologically *after* the transfer) → transfer cost identical between branches, and the destination's final state is **exactly identical** in both branches (verified equal to full precision) — no propagation at all. Case B (backdated purchase entered *before* the transfer) → transfer cost differs, and the destination's final state differs. This confirms the dependency chain is precisely `historical change → source cost → transfer cost → destination state`, with no other path found by which a destination warehouse is affected while its incoming transfer's own recorded cost stays unchanged.

**D-Lemma 4 (chain propagation, W1→W2→W3) — CONFIRMED.** A backdated purchase in W1 was shown to reach W3's average cost through two chained transfers (W1→W2→W3), verified at every downstream W3 checkpoint (e.g., 8 → 10.57, 7.6 → 9.14) — propagation is not confined to the immediately adjacent warehouse.

**Cycle test (W1→W2→W1) — CONFIRMED, the most consequential result of Q2.4.** A backdated purchase in W1 was shown to propagate through W1→W2→W1 and change W1's *own* final average cost relative to its own baseline (9.47 vs. 13.60, verified) — the correction's effect returns to its warehouse of origin through a transfer cycle.

**Classification (as requested):**
| Case | Description | Status |
|---|---|---|
| 1 — local to source only | No downstream propagation | Only the degenerate case with no subsequent transfer — not the general case |
| 2 — source → destination | Confirmed (D-Lemma 3) |
| 3 — source → destination → further warehouses | Confirmed (D-Lemma 4, W1→W2→W3) |
| 4 — warehouse transfer graph (including cycles) | **Confirmed reachable** (cycle test, W1→W2→W1) |

**Principle this establishes — precise formulation, not "warehouse isolation is broken":**
> Warehouse isolation remains an invariant of the inventory *state* calculation, but it is not an invariant of historical-cost *dependency propagation*.

`get_item_stock_summary(item, warehouse)` still computes a specific warehouse's state correctly and in isolation — that invariant is untouched and was never disproven. What this section establishes is a different, orthogonal fact: the cost *inputs* that arrived at that warehouse may themselves have originated in another warehouse via a transfer. This is the distinction between **state isolation** (confirmed intact) and **dependency/impact isolation** (confirmed absent, per the classification below) — two different properties that must not be conflated when this result is cited later in the design.

**Consequence for Q2.6/Q2.7:** Impact Scope determination cannot assume it may stop at a warehouse boundary, and — combined with Q2.3's DISPROVEN result — cannot rely on any local match-based stopping rule within a warehouse either. The cycle result means Impact Scope is not reliably describable as a time interval confined to one warehouse; it may need to be described as a **connected spatio-temporal subgraph** of the item's movements — spanning multiple warehouses linked by transfers, potentially including cycles back through a warehouse already visited. **Warehouse boundaries must not be used as a bounding rule for Q2.7** — a policy that stops impact analysis "once the item leaves the originating warehouse" would be provably unsound, not merely conservative, given the confirmed cycle case. This makes Q2.7's bounding decision even more load-bearing than previously stated, not a smaller concern specific to Finding A alone.

**Same caveats as Q2.3, carried forward unchanged:** exact arithmetic (rounding can only add further drift, never provide a rescue); single-correction model (concurrent overlapping corrections across warehouses are explicitly out of this scope, a Q3 concern); no claim made yet about how this interacts with same-date ordering (Q2.5) when a transfer and a purchase/sale share a date across two warehouses simultaneously — that intersection is not addressed here and should not be assumed resolved by either question independently.

### Q2.6 — Impact Scope Output — **CONCEPTUAL ANALYSIS COMPLETE** (no schema, no threshold, no implementation — a representational question, answered structurally)

**Affected Movement (Q2.2) vs. Impact Scope (Q2.6) — the distinction that was missing.** Q2.2 defined a *predicate* on one movement: is this specific movement's Baseline state different from its Recalculated state? Impact Scope is a different kind of object entirely — not a predicate, but the **structure** that holds everything a Correction Event needs to describe honestly. Conflating the two was the gap: "the set of Affected movements" is necessary but not sufficient as a definition of Impact Scope, for the reasons below.

**1. Is Impact Scope movements only, or movements + documents + warehouses + accounting effects?**
Not a flat set — a **layered hierarchy**, because each level answers a different question an accountant will actually ask:
- **Root cause** — the original data change that triggered analysis (e.g., "backdated Purchase movement inserted").
- **Affected movements** — the set satisfying Q2.2's predicate, reached via dependency (below).
- **Affected documents** — the business-level unit (an Invoice, a Transfer record, an Opening Balance entry) that an affected movement belongs to. This level matters because a document can contain multiple movements (a multi-line invoice), and an accountant reviewing a correction thinks in documents, not internal movement rows — a document is "affected" if any of its movements is.
- **Affected accounting effects** — the derived JournalEntry/account-level consequence (a COGS delta, an inventory valuation delta) tied to an affected movement or document. This level is **not automatic from the movement level** — a Transfer's movements can be Affected (Q2.2) with no accounting effect at all, because transfers create no JournalEntry (confirmed in 3B-5-A's characterization of Finding D). Assuming "affected movement ⇒ accounting correction candidate" would be wrong for exactly this case.

**2/3. Representing a chain or a cycle.** A dependency **graph** (not a list, not a date range) represents both correctly: nodes are individual movements (or, more precisely, per-movement-per-warehouse cost-state checkpoints); edges are (a) temporal succession within one warehouse (movement *i* depends on the state left by the warehouse's previous movement) and (b) transfer edges connecting a source movement to the destination movement it feeds. This was tested concretely, not just asserted: rebuilding the exact chain and cycle scenarios already empirically confirmed in Q2.4 (W1→W2→W3, and W1→W2→W1) as such a graph and computing simple reachability from the root reproduces exactly the warehouses Q2.4 found affected — including the cycle case, where the graph correctly shows the origin warehouse reachable a second time, downstream of itself. **Impact Scope, structurally, is "the reachable subgraph from the root cause" — which can and does contain cycles, per Q2.4.**

**4. Can scope be disconnected?**
Not for a *single* correction, if Impact Scope is defined as reachability from that correction's own root cause — reachability closures are connected by construction; nothing enters the scope that isn't dependency-reachable from the root. Disconnection only becomes a real question when **two separate Correction Candidates exist at once**: if their reachable sets don't overlap, they are simply two separate Impact Scopes (no issue). If they **do** overlap — sharing some downstream movement — that is a genuinely unresolved case: is the overlap one combined Impact Scope, or two Correction Events that both reference a shared movement? Not decided here; flagged as a concrete open question for Q3, more specific than the earlier general mention of "concurrent corrections."

**5. Root cause vs. affected movement vs. affected document vs. affected accounting effect.**
Answered by the layered hierarchy in point 1 above — these are four distinct levels of the same underlying discovery, related by (root cause) → (triggers analysis over) → (affected movements) → (group into) → (affected documents) → (some of which carry) → (affected accounting effects). A Correction Event needs to be able to report at all four levels without collapsing them, because Q1's tiers depend on exactly this separation (a Correction Event can exist — Q1 tier 2 — with affected movements and documents identified, while having zero or an as-yet-undetermined accounting effect).

**6. Overlapping/multiple Correction Candidates.**
Not resolved here (see point 4) — recorded as an open question for Q3, not answered by this section.

**7. Minimum information a Correction Event needs to say "this is what we found" without overclaiming.**
Given Q2.5's finding that ambiguity can produce **multiple** valid candidate recalculated states (not just one alternate value), a Correction Event's representation of "the recalculated state" for a movement inside an ambiguous tie-group cannot be a single value asserted as fact — it must be able to represent "N candidate states exist, chronology basis = assumed" honestly. This is a second, independent structural requirement on Q3's Correction Event (alongside the `chronology_basis` field already required from Q2.5) — a Correction Event needs the capacity to hold a **set** of candidate outcomes for an ambiguous movement, not just one.

**Explicitly not resolved in this section (deferred to Q2.7):** the *size* problem — how large an Impact Scope subgraph is allowed to get before it needs bounding. Q2.6 only answers what the scope *is* structurally; Q2.7 answers what to do when it's large.

**Connection to staleness (carried forward from Q1):** because Impact Scope is now understood as a reachable subgraph rather than a flat set or date range, the staleness question ("does new data invalidate a Pending Event") becomes concrete: a Pending Event goes stale precisely when a new movement would be added as a **node reachable within its recorded Impact Scope subgraph** — not on any unrelated data change elsewhere. This sharpens the earlier staleness principle without changing it.

### Q2.7 — Scope Bounding / Usability — **ANALYSIS COMPLETE; no bound value chosen, by design**

**Termination is guaranteed regardless of bounding policy — stated first to preempt a natural misreading of Q2.4's "cycle."** The dependency graph (Q2.6) has nodes that are actual historical movement *instances*, not warehouse labels. A "cycle" found in Q2.4 (W1→W2→W1) is a cycle *through warehouse labels*, produced by distinct, finite movement records (a purchase, a transfer, another transfer) — it is not a cycle in the movement-instance graph itself, which is always a finite DAG bounded by the item's total historical movement count. Full reachable-subgraph traversal always terminates on its own; the bounding question is entirely about **cost/size**, never about correctness of termination.

**Given Q2.3's disproof, only two mathematically distinguished positions exist — everything else is a graded policy choice between them, not a discovery:**
1. **Full reachable-subgraph recomputation.** Always correct (no information discarded), cost bounded only by the true size of the dependency graph — which Q2.4/Q2.6 established can span multiple warehouses and revisit them.
2. **Any bound short of full traversal** (node-count cap, transfer-hop cap, time-window cap, or some other cutoff) **is an accepted engineering/business tradeoff, not a mathematically safe simplification** — none of the candidate bound *types* below is more "correct" than another; they differ only in what they're easy to explain to an accountant versus what they're cheap to compute.

**Candidate bound types surveyed (menu only — none adopted):**
- *Node/movement-count cap* — stop once N movements have been visited. Easy to reason about size-wise, but the cutoff point is not tied to any accounting-meaningful boundary (a cap could stop mid-warehouse, mid-chain).
- *Transfer-hop / warehouse-visit cap* — stop after crossing K transfers. More aligned with the graph structure found in Q2.4, but arbitrary in the same way — no accounting principle picks a "right" K.
- *Time-window cap* ("only recompute forward N days/periods") — previously deferred pending this very propagation analysis (Q2.3–Q2.6); now that the analysis exists, this remains equally a policy choice, not a newly-justified one — Q2.3/Q2.4 give no reason to believe economic effects respect any particular time window.
- *Progressive/incremental execution* — run the traversal incrementally, allow interruption/resumption, and track completeness explicitly rather than committing to a fixed cutoff in advance. This doesn't avoid the size problem, but it avoids committing to an arbitrary number before real data volume is known — most compatible with the existing benchmark-driven trigger philosophy (P95/50k) already adopted for Q7's background-job question.
- *Human-in-the-loop scope confirmation* — before running a full traversal, present the accountant with a cheap size/shape estimate ("this touches 3 warehouses, ~1,200 movements, includes a cycle") and let them choose to proceed, request a bounded pass, or abandon — makes the correctness/cost tradeoff an explicit human decision rather than a silent system default, directly implementing "correctness determines scope; performance determines execution" instead of quietly inverting it.

**New structural requirement this forces on Q3 — a second, independent confidence axis.** Q2.5 already required a Correction Event to carry a `chronology_basis` (known/assumed) and, per Q2.6, the capacity to hold multiple candidate states under ambiguity. Q2.7 adds a distinct third property: **scope completeness** (full reachable-subgraph analyzed vs. bounded/partial). This is orthogonal to chronology confidence — a result can be `known chronology + complete scope`, `known chronology + partial scope`, `assumed chronology + complete scope`, or `assumed chronology + partial scope`, and these four combinations do not collapse into each other. **Whether a bounded/partial-scope result should be restricted to Q1's lower tiers (Simulation/Correction-Event only, never auto-posted) the same way an `assumed`-chronology result already is — is not decided here, but is now a concrete, named question for Q1/Q3, not a hypothetical one.**

**No threshold, cap, or default bound-type is chosen in this document**, per the explicit instruction — this section's output is the menu and the structural consequence above, not a selected number or policy.

### Q2 — Closure summary (the chain, stated once for the record)
`Q2.3` (no safe local stopping rule exists) → `Q2.4` (effect can cross warehouses and cycle back) → `Q2.5` (same-date ambiguity can yield several valid states, and the ambiguity itself crosses warehouses) → `Q2.6` (Impact Scope is therefore a reachable dependency subgraph, not a time interval or a single warehouse) → `Q2.7` (bounding that scope, when needed, is purely a policy/performance decision layered on top of an already-understood correctness picture — never a redefinition of what "correct" means). Q2 is closed at the conceptual level; no thresholds, schemas, or production code were introduced at any step.

**Three constraints this design must satisfy simultaneously — none may be resolved by silently overriding another:**
- **Accounting correctness** — propagation must not stop before the real economic effect ends.
- **Computational efficiency** — propagation must not recompute history unnecessarily.
- **Human workflow viability** — the scope produced must not make Pending Events effectively unapprovable in an actively-moving business (the concern already raised against Policy C above).

**Governing principle, to prevent performance concerns from quietly becoming accounting rules:**
> Correctness determines the required scope; performance determines how that scope is executed.

If honest propagation analysis concludes a given correction genuinely affects 80,000 downstream movements, that is a fact about the correction, not a defect in the analysis. What happens next — refuse automatic correction, require manual review, or invoke background processing — is Q5's and Q7's decision to make, using that fact as an input. The scope itself must not be shrunk merely because the true answer is computationally or workflow-inconvenient. No solution to the Q2/Q5/Q7/human-workflow tension (e.g., a time-boxed window, "last 30 days," or similar) is adopted here — now that Q2.3–Q2.6 have fully characterized how propagation behaves, it is clear any such rule would remain a policy choice, not a mathematically forced one; understanding propagation did not make any bound "discovered," only made the tradeoff explicit (see Q2.7 above).

## Q3 — Correction Event definition and accounting invariants (not just "which account absorbs the delta")
This question must be answered in order, not skipped to the account-selection part:

**Confidence dimensions carried into Q3, confirmed orthogonal — not to be treated as one concept:**
- `chronology_basis`: known / assumed (Q2.5) — uncertainty in the *order* of events.
- `candidate_states`: single value / multiple candidate values (Q2.5/Q2.6) — a direct consequence of `chronology_basis = assumed`, not an independent axis on its own.
- `scope_completeness`: complete / partial (Q2.7) — uncertainty in whether the *full set* of effects was analyzed at all.

**New open question, explicitly not pre-decided here:** should a `scope_completeness = partial` result be subject to the same restriction already established for `chronology_basis = assumed` (i.e., capped at Simulation/Correction-Event, never auto-posted without explicit accountant approval)? **The two are not interchangeable and must not be conflated by analogy alone**: assumed chronology reflects uncertainty about *the order events occurred in*; partial scope reflects uncertainty about *whether all affected effects were even found*. Partial scope may in some respects be the more dangerous of the two — an incomplete analysis could understate a correction's true accounting impact entirely, not just its ordering — but asserting that without explicit analysis would be exactly the kind of unproven generalization this document has avoided throughout Q2. This is registered as its own decision question for Q3, to be analyzed on its own terms, not resolved by treating it as a restatement of the chronology-confidence policy.

1. **What accounting invariant must the correction preserve?** The original entry has the relationship `Dr COGS / Cr Inventory` for a given amount. If the sale's true cost changes, the correction must preserve `ΔCOGS ↔ ΔInventory` as a matched pair — it cannot become an isolated `Dr Inventory Adjustment / Cr <something unrelated>` that severs that relationship, or the correction stops representing the same economic event it's correcting.
2. **What is a Correction Event?** Per the cascading example in Q1(b): does one correction event correspond to one original document, one date, one account, or one full chain triggered by a single backdated insert? This must be fixed before account selection means anything.
3. **Only then**: which account(s) display the delta? Options remain a dedicated "Inventory Adjustment"/"COGS Correction" account (clean audit trail, possible chart-of-accounts change) vs. reusing the original COGS/Inventory accounts (simpler, more consistent with the *nature* of the correction as an extension of the same economic event, but harder to distinguish "originally posted" from "corrected" in a ledger view later). Reusing the original accounts appears more consistent with invariant #1, but this remains an accounting-policy decision for you to make explicitly, not a default the technical design should impose.

### Q3.1 — Correction Event Granularity — **DECIDED**
Five candidate units were evaluated and four rejected:
- **One Movement** — rejected: fragments a single economic cause into many disconnected events.
- **One Document** — rejected: Q2.6 established a single root cause can span multiple documents; a document-scoped event would be too narrow.
- **One Date** — rejected: a date is not an economic cause and can contain many unrelated movements.
- **One Account** — rejected: an account is an accounting *consequence*, not the causal unit — and Q2.6 established Affected Movement ≠ Accounting Effect (a Transfer can be Affected with no account involved at all), so defining the event around an account would misrepresent what actually happened.
- **One Full Impact "Chain"** — the right idea, but the word is misleading: Q2.4 proved the impact can be graph-shaped (crossing warehouses, including cycles), not a linear sequence.

**Decision:** `Correction Event = Root Cause + Impact Scope`, where Impact Scope is the graph-shaped structure already established in Q2.6 (affected movements, documents, and accounting effects — not assumed linear, not assumed confined to one warehouse).

**Root Cause, clarified beyond the original framing:** not assumed to always be a single newly-inserted movement. Per the system's existing invariant that a POSTED document is never edited in place — only reversed and re-entered (`invoice_edit.py::ensure_editable()`, confirmed in 3B-5-A) — a correction to an *existing* (wrong, not merely forgotten) historical document will take the shape of a **linked reversal + re-entry pair**, not one movement. Root Cause must accommodate both shapes: a single newly-inserted movement (the forgotten-document case) or a linked reversal/re-entry pair (the wrong-document case) — the granularity decision must not be built assuming only the former.

**Correction Event Scope ≠ Accounting Correction Entries** — restated explicitly as its own principle: not every element of a Correction Event's Impact Scope produces a journal entry (a Transfer can be Affected per Q2.2 without any accounting effect at all, per Finding D's characterization). The Correction Event records the full scope; which subset of it becomes actual accounting entries is a separate, later decision (Q1's tier progression), not implied by scope membership.

### Q3.2 — Required Fields (conceptual only — no schema, no storage shape decided)
Ten conceptual field groups, each stating *what a Correction Event must be able to express*, not how it is stored:

1. **Identity** — `correction_event_id`: an identity independent of any single document or movement, since Root Cause (Q3.1) may involve several. No `company_id` or similar added speculatively — not justified by anything decided so far.
2. **Root Cause** — a set of linked *components* (not one field), able to express both shapes from Q3.1: a single newly-inserted movement, or a reversal+re-entry pair. Internal representation (child table, polymorphic relation, etc.) deferred.
3. **Trigger** — `trigger_type`, distinct from Root Cause: describes *how* the event came to exist (e.g. a backdated-insert detection hook, a historical-document correction, a future manual-reconciliation request) — consistent with Q1's Lazy-with-lightweight-hook creation policy, where a cheap Candidate detection is distinct from the later full analysis.
4. **Chronology Confidence** — `chronology_basis` (at least `KNOWN`/`ASSUMED`), first-class per the existing requirement from Q2.5 — never a text note.
5. **Candidate States** — `baseline_state` (the current, immutable, POSTED reality) plus `candidate_states[]` (one or more analytically-derived possibilities, per Q2.5's proof that ambiguity can yield more than two outcomes). A Candidate State is a *result contained in* the Event, not the Event itself. **Added requirement, not in the original proposal**: each candidate state must reference *which tie-group and which assumed ordering* produced it — `candidate_states = [A, B, C, D]` alone is not reviewable; an accountant approving one candidate under Policy C needs to know what distinguishes it from the others, or the approval step is uninformed by construction. This is a semantic gap, not a storage detail — every candidate must carry a pointer back to its originating ambiguity (the specific Q2.5 tie-group and the specific assumed order applied).
6. **Impact Scope** — the Q2.6 graph: nodes (`InventoryMovement`, `Document`, `AccountingEffect`) and relationships (`causes`, `precedes`, `propagates_to`, `belongs_to`, `produces_accounting_effect`). Storage shape (graph table, adjacency list, etc.) not decided here — only the semantic requirement.
7. **Scope Completeness** — `scope_completeness` (`COMPLETE`/`PARTIAL`), confirmed orthogonal to chronology_basis — all four combinations (known/complete, known/partial, assumed/complete, assumed/partial) are meaningful and distinct; the policy governing what each combination permits is a separate later decision, not Q3.2's job.
8. **Temporal / Analysis Metadata** — `trigger_date` (when detection occurred, if meaningful) and `analysis_as_of` (the data state the analysis was computed against) — enough to answer "what data was this result computed from," which is exactly what the staleness principle (Q1) needs, without building a general data-versioning system.
9. **Overlap Detection** — no stored `overlap_status` (deliberately — a derived fact risks becoming stale metadata). Instead, Impact Scope's node references must be structured so that `Scope(CE-A) ∩ Scope(CE-B)` is computable on demand. Purely a structural requirement — the policy for handling a detected overlap remains undecided, per Q3.1.
10. **Lifecycle State** — `status` following Q1's lifecycle exactly (`CANDIDATE → ANALYSIS → PENDING → APPROVED → ACCOUNTING_CORRECTION`, with `STALE` routing back to `ANALYSIS`, not a terminal state). Accounting Correction is a distinct subsequent phase, not merely `status = APPROVED`.

**Second added requirement, not in the original proposal — item scope boundary is undecided.** Every Q2.1–Q2.7 test was conducted for a single item across multiple warehouses. But a single multi-line purchase invoice can cover *several unrelated items*, each with its own fully independent `get_item_stock_summary` and its own independent propagation graph (items never share cost state — confirmed invariant). This raises a genuine, unaddressed boundary question: **does one Correction Event ever span multiple items** (bundling several items' independent analyses because they share one triggering document), **or is a Correction Event always scoped to exactly one item**, with a multi-item document producing several separate Events automatically? Neither the granularity decision (Q3.1) nor this field list resolves it, and `baseline_state`/`impact_scope`'s meaning is ambiguous until it's settled — flagged as an open question for the next round, not assumed either way.

**Explicitly not decided in Q3.2 (per your own list, preserved unchanged):**
- **A.** Whether `root_cause` is one entity or a set of linked components — leaning toward the latter, but storage shape deferred.
- **B.** The size/granularity of a candidate state (full per-warehouse state vs. deltas only) — deferred to Q3.3/Q3.4, since it depends on what review and execution actually need.
- **C.** Whether Accounting Effects are part of Impact Scope or an external reference — conceptually part of scope, but its representation waits on Q3.3's accounting invariant (`ΔCOGS ↔ ΔInventory`) being fully specified first.

**Explicitly deferred, not resolved by this decision:** if two *independent* root causes produce overlapping Impact Scopes (e.g., two unrelated backdated purchases both eventually affecting the same downstream sale), they must not be automatically merged into one Correction Event merely because their scopes intersect — this is an "Overlapping Correction Events" question, already flagged as open under Q2.6, and remains open here. **Carried forward as a structural requirement on Q3.2 (not a policy decision):** whatever fields Q3.2 defines for a Correction Event must make it *possible to detect* an overlap between two events' scopes later, even though the *policy* for what to do about a detected overlap stays undecided.

### Q3.3 — Candidate State Representation + Baseline/Delta + Accounting Invariant

**Q3.3.1 — What does a Candidate State represent?**
**Delta-primary, with Baseline held by reference, not copied.** This is not an arbitrary storage preference — it is the direct extension of the principle Q3.2 already established for overlap detection ("store what represents the truth/input, compute derived relations when needed"). Baseline is the current, immutable, POSTED reality — already fully available by referencing the live `InventoryMovement`/`JournalEntry` records; duplicating it into the Event would create exactly the kind of stale-copy risk the overlap-detection decision deliberately avoided. A "full recalculated snapshot" is not independent information either — it is trivially `baseline + delta` by definition, so materializing it as a third stored form would be redundant. Conceptually: `CandidateState = reference-to-baseline + delta-vector + provenance (Q3.3.3)`; a full "recalculated view" is a computed presentation for review, not a fourth stored fact.

**Q3.3.2 — Baseline/Candidate relationship, and the derived-vs-primitive caution.**
A Candidate State must be able to answer three questions per affected node: what was the state without the root cause (baseline, by reference), what does it become under this candidate's assumption (derived: baseline + delta), and what changed economically (the delta itself). The explicit caution carried over from Q2.2 applies with full force here: not every component of the Q2.1 state vector that differs is an independently meaningful economic fact — some are algebraically derived from others, and treating each as its own "difference" would misrepresent one cause as several.

**Q3.3.4 — Delta Representation: which deltas are primitive, which are derived (answered concretely, not just surveyed).**
Re-examining `accumulate_average_cost()`'s own algorithm (Q2.1/3B-5-B) settles this precisely: the function tracks exactly **two** independent running accumulators — `total_qty` and `total_cost` (= inventory value). Everything else in the state vector is a deterministic function of those two plus a specific movement's own parameters:
- `average_cost = inventory_value / quantity` — derived.
- `movement_unit_cost` for a subsequent OUT — derived (it *is* the average cost at that point).
- `cogs_consequence` — derived (`movement_unit_cost × quantity` for that OUT).

**Only `Δquantity` and `Δinventory_value` are primitive facts worth independent representation.** Everything else should be a computed view, not separately stored — the same "don't store derivable truth" principle applied a second time, now to the math itself rather than to baseline-copying.

**Further simplification, verified computationally, not merely asserted:** `Δquantity` is not just primitive — it is **regime-constant**. Rebuilding the exact multi-hop chain scenario from Q2.4/D-Lemma 4 and tracking `Δquantity` at every subsequent step (including additional, independent purchases and sales added *after* the transfers) shows it holds at exactly one constant value for the entire span within a warehouse, changing only at a transfer crossing (verified: `ΔQ(W1) = 40` unchanged across 9 steps including new unrelated W1 purchases; `ΔQ(W2) = 0` and `ΔQ(W3) = 0` throughout, unaffected by independent W2/W3 activity after their respective transfers). **Practical consequence: `Δquantity` does not need per-movement storage at all — only per "quantity-regime segment" (the root cause itself, and each transfer crossing where it can reset to a new constant, e.g., to 0 on the receiving side).** `Δinventory_value`, by contrast, is not regime-constant (Q2.3's disproof showed it can shift with every subsequent IN) and does need per-movement representation.

**Scope-limiting correction to the above, stated precisely so it is not over-extended:** `Δquantity`'s regime-constancy must **not** be read as "the delta reduces to a single warehouse segment" in any broader sense. `ΔInventoryValue` remains sensitive to the full cost sequence and is *not* confined by warehouse boundaries the way `Δquantity` is — a Transfer resets `Δquantity`'s regime, but per Q2.4, it is exactly the *conduit* by which the underlying value/cost discrepancy propagates into another warehouse's own regime, not a point where the economic effect stops. **A Transfer is a boundary for `Δquantity` distribution; it is not a boundary for the total economic effect** — fully consistent with, and precisely restating, Q2.4's own finding.

**Q3.3.3 — Candidate Provenance, made concrete.**
Each Candidate State must reference: (a) the specific Q2.5 tie-group (the set of same-date movements whose order was ambiguous) it depends on, and (b) the specific assumed ordering chosen within that tie-group — expressed in terms of Q2.5's own reduced representation (the run-collapsed interleaving, not a raw permutation index, since that reduced form is the one already established as the meaningful description of an ordering choice). Without this, `candidate_states = [A, B, C, D]` remains unreviewable, exactly as flagged in Q3.2.

**Q3.3.5 — Accounting Invariant, refined beyond a naive per-movement pairing.**
Your caution was correct: `ΔInventoryValue = −ΔCOGS` does not hold *per movement* in general — a Transfer's `ΔInventoryValue` has no `ΔCOGS` counterpart of its own (transfers create no journal entry at all, per Finding D), and its value effect only "closes the loop" once a downstream sale elsewhere in scope, consuming that transferred stock, is itself corrected. **The correct invariant is scope-level, not movement-level:** for any subset of the Impact Scope that is converted into an Accounting Correction, the sum of all `ΔInventoryValue` effects posted to inventory accounts must exactly offset the sum of all `ΔCOGS` effects posted to COGS accounts for that same subset — ordinary double-entry conservation applied to a correction instead of an original transaction, evaluated over the chosen subset as a whole, not movement-by-movement.

**Newly surfaced consequence for the open Partial-Scope question (Q2.7/Q3):** this conservation property is **only checkable when the scope is complete**. If `scope_completeness = PARTIAL`, some value may have left the analyzed boundary without a matching accounted exit yet being discovered, and the invariant cannot be verified to hold. This is a concrete, mechanical reason — not merely "extra uncertainty" — that strengthens (without yet deciding) the case for restricting `scope_completeness = PARTIAL` results the same way `chronology_basis = ASSUMED` results are already restricted: an unverifiable invariant is a stronger objection to auto-posting than an unresolved ordering assumption. Still not decided here, per Q3's own registration of this as an open question — but no longer an unsupported hypothesis.

**Q3.3.6 — Granularity of the delta.**
Computed at movement granularity (the level `accumulate_average_cost()`'s own math actually operates on), then **aggregated upward** for review: movement deltas roll up to their document (sum of a document's movements), and the subset with a genuine accounting effect rolls up further to account-level entries. The Correction Event must expose all three views on demand, not force a reviewer to read raw per-movement deltas one at a time — but only the movement-level figures are independently computed; document- and account-level figures are aggregations, not separately derived facts.

**Q3.3.7 — Multiple Candidates: must each be globally consistent, and a new size dimension this reveals.**
Each `candidate_states[]` entry must represent **one complete, internally consistent resolution of every ambiguous tie-group within the Impact Scope simultaneously** — not a locally valid fragment. A candidate that only resolves one tie-group without regard to how that choice interacts with a second, independent tie-group elsewhere in the same scope is not a valid candidate; it is an incomplete one. **This surfaces a size dimension Q2.7 did not address**: if an Impact Scope contains multiple independent ambiguous tie-groups, the true candidate space is their **cross-product**, not their sum (two tie-groups with 3 resolutions each yield up to 9 globally consistent candidates, not 6) — unless some combinations are provably equivalent, which is not established here. This is registered as an amendment to Q2.7's scope-size discussion: Impact Scope can be large in *movement count* (Q2.7's original concern) and, independently, large in *candidate count* — these are two different size problems, both real, neither resolved by the other.

### Q3.4 — Accounting Effect & Correction Invariant

**Three distinct concepts, deliberately separated:**
1. **Inventory Delta** — the change in inventory state (`Δquantity`, `Δinventory_value`) produced by recalculation — a pure fact about stock, established in Q3.3.
2. **Costing Delta** — the change in the cost assigned to OUT movements, and therefore in `ΔCOGS` — derived from (1) per Q3.3.4's algebra, not independent.
3. **Accounting Correction Effect** — the journal entry, if any, chosen to represent a subset of (1)/(2) in the ledger — a policy-mediated translation, not automatic from (1)/(2) alone.

**Does every ΔCOGS need to produce an Accounting Correction?** Not as an invariant — a nonzero `ΔCOGS` on a POSTED sale is a real misstatement and a *candidate* for correction, but whether it is actually converted into a posted entry is governed by Q1's tier/approval policy and Q5's materiality threshold, neither decided here. Q3.4's job is narrower: *if* an Accounting Correction is created for a given `ΔCOGS`, what must it satisfy (see the invariant below) — not whether one is mandatory.

**Does every ΔInventoryValue need to produce an Accounting Correction?** This closes a gap Q3.3.5 left open. Unsold stock's `ΔInventoryValue` sits on the balance sheet, not in COGS — if the ledger's Inventory account is meant to reflect corrected reality, an inventory-valuation correction is the symmetric counterpart to a COGS correction for stock still on hand. This completes Q3.3.5's scope-level invariant into a proper three-way identity, the same one that governs ordinary inventory accounting: **`Δ(inputs entering the scope, i.e. corrected purchase/IN costs) = Δ(COGS recognized within the scope) + Δ(ending inventory value remaining within the scope, across every warehouse touched)`.** This is a strict generalization of Q3.3.5's two-way pairing, not a replacement — it resolves exactly the ambiguity Q3.3.5 left unresolved about where a Transfer's or an unsold purchase's value effect goes.

**How is a Transfer, which has no JournalEntry, handled?** Consistently with the identity above: a Transfer is never itself a source of an Accounting Correction (it has no journal entry to correct, per Finding D) — it is purely a **conduit**. Its `Δquantity`/`Δvalue` effect is not lost; it flows into whichever warehouse it lands in and eventually surfaces as *that* warehouse's own ending-inventory-value delta (if the transferred stock is still on hand) or COGS delta (once it's sold). No separate "Transfer correction" concept is needed or should be introduced.

**What if the net ΔCOGS on a specific sale is zero despite internal path changes?** This can genuinely happen, and must be recorded honestly rather than smoothed over: a zero `ΔCOGS` at one node means *that specific* OUT's cost coincided between Baseline and Recalculated (per Q2.3's Lemma 2, this exact coincidence is precisely the "local match" scenario already proven insufficient to guarantee anything about later nodes). Two things must both be true in the record: (a) this specific movement warrants no accounting correction of its own, and (b) this fact must **not** be used to stop analyzing what comes after it — exactly the discipline Q2.3 already established, now applied at the accounting-effect layer instead of the raw state-vector layer.

### Q3.5 — Account Selection Policy (accounting policy, not schema)

**Q3.5.1/3.5.2/3.5.3 — Which accounts for ΔCOGS and ΔInventory, and original vs. dedicated.**
Grounded in the actual chart-of-accounts structure (not assumed): each `Item` already carries its own `cogs_account_id` and `inventory_account_id` (confirmed in the codebase). This has a direct, concrete consequence for the "original vs. dedicated" choice: **reusing the original accounts requires zero new configuration** — the mapping already exists per item. A **dedicated correction account**, by contrast, forces a further choice that doesn't arise for the original-account option: one shared correction account for *all* items (loses item-level traceability in the ledger) or a dedicated correction account *per item* (doubles the relevant part of the chart of accounts). This is decision-relevant information, not a decision — the original-account option is structurally simpler by default; whether the audit-trail clarity of a dedicated account is worth that added configuration is a policy call, not a technical one.

**These two choices (COGS account, Inventory account) are independent, not one bundled decision.** Nothing requires a symmetric answer — a company could reuse the original COGS account (since COGS naturally flows through the same period's P&L either way) while still preferring a dedicated Inventory Adjustment account (for balance-sheet clarity on corrected valuations). Four combinations exist (original/original, original/dedicated, dedicated/original, dedicated/dedicated); none is technically favored by anything established so far — this is registered as an open combinatorial choice, not collapsed into a single either/or.

**Q3.5.4 — The unsold portion must have an explicit, matching entry — and this is not merely good practice, it is mechanically forced.** Directly following Q3.4's three-way identity: whatever part of the corrected-input delta hasn't flowed into `ΔCOGS` must be represented against the Inventory (or Inventory Adjustment) account chosen in Q3.5.2, or the entry cannot balance at all. This isn't a new safeguard to design — the existing accounting boundary already enforces `is_balanced()` at posting time for every journal entry (confirmed in `sanity_guard.py`, invoked from `posting.py`'s existing reversal path) and would apply identically to any future Accounting Correction, since it would go through the same Boundary as every other posting in this system. A correction entry that only posts the COGS side and omits the inventory side would simply fail to post — the existing mechanism already forecloses that failure mode; Q3.5.4 only establishes that the *semantic content* (not just the arithmetic balance) must include both sides.

**Q3.5.5 — A correction with no journal entry at all must be explicitly representable, not an omission.** Already true by construction throughout this design (a Transfer's Affected status, an `ASSUMED`-chronology or `PARTIAL`-scope result held at a lower Q1 tier, a zero-`ΔCOGS` node) — restated here as a hard rule specific to Q3.5's account-selection question: **`Affected` must never be silently interpreted as `⇒ post a journal entry`.** Account selection only becomes relevant once a specific economic effect has actually been approved for conversion to an Accounting Correction — it has no bearing on whether that conversion happens at all.

**Q3.5.6 — The final invariant is stronger than "the entry balances," and the balance half is already guaranteed by existing infrastructure.** The mechanical half — debits equal credits — is already enforced unconditionally by the existing Boundary (`is_balanced()`) for any journal entry, correction or otherwise; this is not new work. What **is** new, and must be the actual gate condition for the Analysis → Accounting Correction transition (Q1's tier boundary), is a **reconciliation check**: `Σ(posted ΔCOGS entries) = Σ(analyzed ΔCOGS for the corrected subset)` and `Σ(posted ΔInventory entries) = Σ(analyzed ΔInventoryValue for the corrected subset)` — i.e., does what was actually posted match what was actually approved from the analysis, not merely "is the posted entry internally balanced." This directly operationalizes **Correction Completeness** (Q3.4): the gate must be able to certify, for whatever subset of the Impact Scope is being converted this time, that the posted entries fully and exactly account for that subset's economic delta — no more, no less — leaving any remaining uncorrected delta explicitly tracked rather than silently absorbed or dropped.

## Correction Event — Semantic Audit (whole-entity review, no new fields added speculatively)

Ten areas checked against everything decided in Q1–Q3.5. Eight pass unchanged; two required actual resolution during this audit rather than mere confirmation — flagged as such below.

**1. Root Cause** — PASS. Can represent a single newly-inserted movement or a linked reversal+re-entry pair, per Q3.1; nothing assumes a single `InventoryMovement` as the only shape.

**2. Item Scope — RESOLVED here (was left open since Q3.2).** Items never share cost state (`get_item_stock_summary` is strictly per-item; confirmed invariant since 3B-5-A) — there is no dependency edge, of any kind established in Q2.4/Q2.6, that ever connects one item's movements to another's. This means Impact Scope's own definition — a *reachability closure* in a dependency graph (Q2.6) — settles the question on its own terms, not by a new rule: a "scope" spanning two items would never be a single connected reachable set; it would trivially decompose into disconnected components, which is exactly the case Q2.6 already said should not occur for one Correction Event. **Decision, derived from an existing principle rather than newly invented: one Correction Event = one item's Impact Scope, always.** A multi-line purchase invoice touching several items produces **multiple** Correction Events (one per item), each referencing the same originating document within its own Root Cause — linked for traceability, but independently reviewable, analyzable, and approvable units, consistent with Q3.1's earlier rejection of "Document" as the granularity axis.

**3. Candidate States** — PASS, all four sub-criteria already established: globally consistent per Q3.3.7, traceable to tie-group + assumed order per Q3.3.3, delta-primary per Q3.3.1, compared to baseline without storing unnecessary derived values per Q3.3.1/Q3.3.4.

**4. Impact Scope** — PASS. Closure over movements/documents/accounting-effect nodes with transfer edges, per Q2.6/Q3.1; overlap expressible via scope-reference comparison without a stored `overlap_status`, per Q3.2.

**5/6. Scope Completeness vs. Correction Completeness** — PASS, and confirmed still cleanly separated: the former is an analysis-time property (Q2.7 — was everything analyzed?), the latter an execution-time property (Q3.4/Q3.5.6 — of what was analyzed, how much was actually posted, verified via the reconciliation check). Neither is redundant with the other; both remain independently necessary.

**7. Economic Effect vs. Accounting Effect** — PASS. Kept separate since Q1/Q3.1, refined precisely in Q3.4/Q3.5 — Economic Effect (Inventory Delta + Costing Delta) exists independently of whether any Accounting Correction is ever created for it.

**8. Chronology Basis independent of Scope Completeness** — PASS. All four combinations (`known/complete`, `known/partial`, `assumed/complete`, `assumed/partial`) remain live and unprejudiced; no policy governing which combinations permit which Q1 tier has been decided, by design (registered as open in Q3's introduction).

**9. Lifecycle — gap found, flagged here.** The `Pending → Stale → Analysis` cycle (Q1) is sound as far as it goes, but it only covers *analyzed* events becoming outdated. A **Candidate** — created by the cheap detection hook, before any full Analysis has run — has no analysis result to go "stale" in the sense Q1 defined (staleness was specifically defined as a *stored analysis result* no longer matching current data; a bare Candidate has no such result yet). But a distinct, real scenario exists: the condition that caused a Candidate to be flagged can stop applying before the accountant ever requests full analysis (e.g., the triggering backdated movement itself is later reversed/removed). This is not "Stale" — it is closer to **Withdrawn / No Longer Applicable**, a dead-end requiring no re-analysis, since none was ever performed. **This is a genuine addition to the lifecycle, not a restatement**: `CANDIDATE → WITHDRAWN` (terminal, distinct from `PENDING → STALE → ANALYSIS`, which recycles). Registered as a finding of this audit — not decided as final wording, but the gap itself is real and should not be left unaddressed when the lifecycle is eventually specified as schema.

**10. Overlap** — PASS. Comparable via Impact Scope node references (Q3.2); no stored overlap policy or status, consistent with the "detectable, not decided" principle established since Q3.1.

### The final test: what must be stored as analytical history, versus computed, versus referenced?

Three categories, not two — this is the audit's most consequential finding, because it resolves the ambiguity in "store the fact, compute the derived value" by identifying exactly *why* that principle applies to some fields and not others:

- **(a) Immutable facts, referenced, never copied** — `InventoryMovement`/`JournalEntry` records themselves (Baseline). Safe to reference forever because they never change once POSTED.
- **(b) Pure derivations from always-*live*, always-current data — never stored.** `average_cost` computed by `get_item_stock_summary` right now is correct *by definition* for "now" — there is no notion of a stale "current average," because it is defined as whatever the live data currently says. Re-deriving it on demand is always correct.
- **(c) Analytical history — results that were computed against a *specific past data state* and must be preserved, because re-deriving them later is not guaranteed to reproduce the same answer.** This is the category `average_cost` does **not** belong to, but `candidate_states` **does** — and the reasoning is precise, not just an analogy to "the accountant's choice matters": a Candidate State is the output of an analysis run at a specific `analysis_as_of` point. If new movements are added afterward, re-running the same analysis *later* can legitimately produce a *different* result — that is not a bug, it is exactly what Staleness (Q1) already exists to name. **A concept can only meaningfully be called "stale" if it was stored** — a live query is never stale, only a preserved snapshot can be. This is why `candidate_states`, their provenance (tie-group + assumed order, Q3.3.3), `analysis_as_of` itself, every lifecycle transition and approval decision, and the Correction Completeness record (what subset was actually posted, Q3.5.6) all belong in category (c): each represents a *decision or a frozen analytical conclusion*, not a value re-derivable safely at any future point from currently-live data alone.

This three-way split is the structural principle the eventual schema (Q3.6 or beyond) must implement — not a new decision being made here, but the criterion that resolves *which* of Q3.1–Q3.5's many concepts fall into which of the two storage buckets the project has been using informally throughout ("store what represents truth or history; compute what's derivable") — now made precise enough to apply without re-litigating it field by field.

**What exact invariant must hold after a Candidate is converted to an Accounting Correction?** The three-way identity above, evaluated over whatever *subset* of the Impact Scope is actually being converted — which surfaces a distinction not previously named: **scope completeness (Q2.7, an analysis-time property — was everything analyzed?) is different from correction completeness (new here — of what was analyzed, how much was actually posted?).** Correcting only part of an affected chain (e.g., 3 of 5 affected sales, deferring the rest to manual review) means the three-way identity does not fully close for the whole scope — the uncorrected remainder's delta must remain tracked (not silently dropped), so that if/when the rest is corrected later, the identity can still close rather than double-count or lose value. This is a genuine open design point for the eventual Correction Event fields, not resolved here — flagged as a fourth confidence-adjacent dimension, distinct from `scope_completeness`, `chronology_basis`, and `candidate_states`.

**Should Correction Event keep economic effect separate from accounting effect?** Yes — and this is the same principle already established twice (Candidate State ≠ Accounting Correction in Q1; Correction Event Scope ≠ Accounting Correction Entries in Q3.1), now made precise at one more level: the **economic effect** (the Inventory Delta and Costing Delta — a factual, analysis-derived quantity) must be recorded independently of the **accounting effect** (the specific journal entry, if any, chosen to represent some subset of that economic effect, following whatever account-selection and granularity policy is decided later). Collapsing them would mean the Correction Event could no longer honestly represent a case where real economic effect exists but no accounting entry has yet been (or ever is) posted for it.


## Mandatory prerequisite (not an open question, not deferrable): deterministic chronological ordering — **RESOLVED, see the DECIDED section below**
This was Q4 in the prior draft — re-framed because it isn't one design option among several to weigh later. A correction engine cannot state "this movement is downstream of that one" without first knowing what order movements occupy when `movement_date(A) == movement_date(B)`. No correction algorithm design can start before this is fixed.

**`(movement_date, document_type_priority, id)` is explicitly not adopted as the default here.** It was raised in the prior draft as one candidate, but `document_type_priority` silently invents a business chronology that may not hold — e.g., it would need to assert "a purchase always precedes a same-day sale," which is false whenever the purchase is entered *after* the sale but backdated to the same day. Fixing a priority order without first answering what kind of chronology is being modeled would smuggle in an assumption disguised as a technical default — exactly the trap already avoided once for Finding B in 3B-5-A ("do not assume `id` is the answer just because it's monotonic").

The prior question must be answered first: **is the intended ordering business occurrence, data-entry chronology, or accounting-processing chronology?** These are three different, legitimate notions of "when something happened," and same-date ties will sort differently under each. Only once one is chosen does it become meaningful to ask what column(s) implement it — a new explicit sequence populated at insert time, a chosen document-type rule (only after "business occurrence" is confirmed as the intended semantics and the rule is validated against real scenarios like the purchase/sale example above), or something else.

## DECIDED — Chronology semantic (mandatory prerequisite, resolved)
**Chronology semantic: Business Occurrence.** `movement_date` represents the economic/business date the movement occurred, not the data-entry date — deliberately, so a late-entered backdated purchase is treated as a correction to historical data, not as a purchase that "happened" on entry day. This corrects the previous draft's overreach: IAS 2 governs the *costing method* (weighted average, periodic or per-delivery), not how a same-date tie is resolved inside a specific system — that resolution is engineering/accounting policy, not a standard requirement.

**For movements sharing the same `movement_date`, the system must not treat database/insertion order (`id`, SQLite scan order, entry timestamp) as economic chronology.** A deterministic costing tie-break policy (e.g., IN-before-OUT) *may* be used when true intra-day occurrence is unknown, but any such rule is explicitly an **Assumed Costing Order** for costing/reconciliation purposes — never a claim of discovered historical fact. **No specific tie-break rule is adopted now** — not IN-before-OUT, not any other — because for this business's actual transaction volume (multiple same-day purchases/sales/returns/transfers per item across three restaurant concepts), same-date ties are the normal case, not an edge case, and committing to an unvalidated rule now risks either inventing false certainty or making automatic correction unusable in practice. The rule, its scope, its confidence signaling, and its refusal threshold are deferred to Q2.5 below.

## Q2.5 — Tie Resolution / Ambiguity Analysis — **ANALYSIS COMPLETE, findings below; no tie-break rule adopted**
Before any correction executes, the design must answer:
- **How is "this tie is cost-impactful" detected without brute-force permutation checking?** Testing every ordering of *n* tied same-date movements is factorial (5 movements → 120 orderings; 10 → 3,628,800) — infeasible as a general mechanism. The actual question is narrower: "does a different tie order among these specific movements produce a materially different cost-state outcome," which should be derivable from movement types and quantities directly, not from exhaustive enumeration. **Answered below — partially: a real, provable reduction exists, but it does not collapse to a small polynomial-size check in general.**
- What is an acceptable bound on the number of ambiguously-tied movements before ambiguity analysis itself becomes the bottleneck? Not answered — depends on the reduction's actual savings in real data, not yet measured.
- When (if ever) is an Assumed Costing Order applied automatically, versus when does ambiguity force a refusal requiring manual review? Not decided here — a Q2.5/Q5 policy decision, deliberately deferred.
- **How is a result's chronology basis surfaced to the accountant?** Unchanged from before — structural requirement on Q3.
- **This is a distinct threshold from Q5.** Unchanged from before.

### 1. Tie classes examined
IN–IN, OUT–OUT, IN–OUT/OUT–IN (mixed), and Transfer-as-OUT/Transfer-as-IN at each side of a cross-warehouse tie. Return movements were not separately tested — per the existing scope decision, Finding C/Returns stays out of this design track entirely, so Return-involving ties are noted as unexamined by choice, not overlooked.

### 2. Pairwise ordering effects
- **IN–IN**: commutes exactly (verified: identical result both orders) — addition is order-independent regardless of the specific costs involved.
- **OUT–OUT**: commutes exactly (verified) — because an OUT never changes the average cost (established in Q2.3's Lemma 2), a sequence of OUTs subtracts at the same average regardless of order.
- **IN–OUT**: **does not commute in general.** The first pairwise test run showed a false "commutes" result — traced to a numeric coincidence in the test data (the inserted purchase's cost happened to exactly equal the pre-existing average, which trivially leaves the average unchanged either way). Rerun with a distinguishing cost value: `IN(cost=40)` before vs. after `OUT(4)` against a base average of 10 produced **different results** (520 vs. 560) — confirmed non-commutative in general. This self-correction is recorded explicitly rather than left as the original (wrong) finding.

### 3. Multi-movement ordering effects
The first hypothesis tested — "only the IN/OUT interleaving skeleton matters; which specific IN or OUT occupies a given same-typed slot is free" — was **tested directly and refuted** (a 2-IN/2-OUT case produced 8 distinct results across only 6 skeleton patterns, meaning results varied even within one fixed skeleton). The refined hypothesis — **within the plain-IN/plain-OUT model tested here, movements commute only within a maximal *consecutive* run of the same type; non-adjacent same-type movements separated by an opposite-type movement are not provably interchangeable** — was tested and holds across three constructed skeletons (a 2-run skeleton showing full internal freedom → 1 result; a fully-alternating skeleton showing no freedom → 4 distinct results; a mixed skeleton showing exactly the freedom accounted for by its one internal run and no more). **This is a result of the specific model and movement types tested (plain IN/OUT, and Transfer treated as OUT+IN) — it is not yet proven as a general theorem covering every `InventoryMovement` type or combination (e.g., Returns were not included per the existing scope exclusion). It should be read as "confirmed for the cases examined," not "proven true in general."**

### 4. Transfer-related ordering effects
A same-date scenario (W1 Purchase, W1→W2 Transfer, W2 Purchase, W2 Sale) was permuted across all valid (non-overselling) orderings: **3 distinct final states for W2 emerged, depending on whether the W1 purchase was resolved before or after the transfer within W1's own tie order.** This confirms that same-date ambiguity is not confined to a single warehouse — resolving a tie inside the source warehouse can change what cost a destination warehouse receives, coupling the tie-resolution problem itself across warehouses (a different, additional finding from Q2.4's propagation-of-an-already-fixed-cost result — here the *ambiguity itself*, not just a confirmed difference, crosses the warehouse boundary).

### 5. Proven order-insensitive cases
- Any maximal consecutive run of pure IN movements (any length, any costs).
- Any maximal consecutive run of pure OUT movements (any length, any quantities) — a direct consequence of OUT never changing average cost.

### 6. Proven order-sensitive cases
- Any IN adjacent to (or separated only by same-type runs from) an OUT, where the IN's cost differs from the average that would otherwise apply — confirmed non-commutative, and confirmed to compound across 3+ movements (the requested Purchase/Sale/Purchase/Sale scenario produced **4 distinct final inventory values across 7 valid orderings** — not merely "ambiguous," but ambiguous with more than a binary set of possible outcomes).
- Cross-warehouse: a tie inside a source warehouse touching a same-date transfer, as in point 4.

### 7. Mathematical/combinatorial shortcut discovered
**Real, but partial.** The safe reduction is: partition a tie-group into its maximal consecutive same-type runs; only permutations *within* a run need not be enumerated (they're guaranteed identical). This is a genuine, provable savings — but for a tie-group that alternates types with no long runs (plausibly common in a busy restaurant, where purchases and sales interleave through the day), the reduction saves nothing, and the full combinatorial space remains.

### 8. Whether ambiguity can be detected without n! enumeration
**Partially yes, partially no** — stated honestly rather than rounded up: detecting that *some* ambiguity exists can be done cheaply (any IN adjacent-or-connected to an OUT within a tie-group is a candidate for sensitivity, checkable without enumeration). Determining the *exact number and nature* of distinct possible outcomes, however, still requires enumeration over the reduced (run-collapsed) space in the general case — no further shortcut was found or is claimed.

### 9. Remaining unresolved questions
- The acceptable bound on tie-group size before this analysis itself becomes a bottleneck (needs measurement against realistic data, not assumed).
- Whether a bound tighter than "run-collapsed enumeration" exists for specific, common realistic patterns in this business's actual data (not investigated — would require real transaction samples, not synthetic ones).
- How tie-resolution ambiguity interacts with Q2.6's Impact Scope definition when a tie-group spans a transfer graph with cycles (Q2.4's result) — not yet examined jointly.
- Whether Return-involving ties (excluded here per the Finding C scope decision) would introduce any different structural behavior — deliberately left for the independent Returns track, not this document.

### 10. Test results
This is exploratory mathematical analysis conducted outside the application (no test files added to the project, no `pytest`/characterization suite changes) — the existing 8/8 characterization / 42/42 regression / 200/200 fuzz results are unaffected because no production code was touched.

### 11. Production code changed
**0 files.** All analysis in this section was performed in standalone scripts outside the repository, used purely to inform this document.

**Open link to Q1, surfaced by this decision:** should chronology confidence gate which Q1 outcome is permitted? Concretely — a *known*-chronology result may be eligible for Q1(b) (an actual additive accounting correction), while an *assumed*-chronology result may be restricted to Q1(a) (reconciliation/simulation only) unless the accountant explicitly reviews and approves promoting it to a posted correction. This is not decided here — it is flagged as a question Q1's design cannot ignore once chronology confidence exists as a concept.

**Structural consequence for Q3 (Correction Event), carried forward unchanged:** whatever record structure Q3 defines for a Correction Event must carry a chronology-basis field (e.g., known vs. assumed) as a first-class part of the event from the moment it's designed — not layered on afterward.

### Closing synthesis — the precise claim this analysis supports (and does not)
> Q2.5 established that some safe reductions exist to shrink the ordering space, but it did not establish a general algorithm that avoids worst-case permutation complexity. The system must not be designed on the assumption that ambiguity analysis will always be cheap.

This is deliberately weaker than "we can detect ambiguity efficiently" — that stronger claim is not supported by what was tested and must not be asserted. This finding is an input to Q2.7, Q5, and Q7 (all three now inherit a real possibility of expensive-in-the-worst-case ambiguity analysis, not merely expensive propagation).

**Ambiguity's effect is not binary.** The requested Purchase→Sale→Purchase→Sale scenario produced **4 distinct final states from 7 valid orderings** — same-date ambiguity does not mean "the answer could be A or B," it can mean several genuinely different historical cost states are all consistent with the same set of same-date documents. And per the Transfer test, this ambiguity — not just a fixed downstream *effect* as Q2.4 established, but the *ambiguity itself* — can cross warehouse boundaries: which order a source warehouse's same-date tie is resolved in can change which of several possible states a destination warehouse ends up in. Q2.5 and Q2.4 are therefore linked at a deeper level than "both involve warehouses": an unresolved tie at one graph node can leave downstream nodes with their own unresolved multiplicity, not just a confirmed single difference.

**This does not decide the Assumed Costing Order, and must not be read as doing so.** `movement_date` remains Business Occurrence (decided earlier); when two movements share a date, Business Occurrence is simply `unknown` between them, and any order chosen thereafter is an **Assumed Costing Order**, not a discovered historical fact — fully consistent with "the system corrects the history it knows, and does not invent the history it doesn't." No default (IN-before-OUT or otherwise) is adopted here or implied by anything in this section.

## Principle: recalculation does not authorize mutation of historical POSTED facts
This must appear explicitly in 3B-5-C's design, not stay implicit. The system currently has two kinds of immutable historical fact: `InventoryMovement` (append-only) and a POSTED `JournalEntry` (never edited in place). A correction engine's impact analysis may *conclude* "this sale's true COGS was 120, not 100" — but reaching that conclusion is a **derived, recalculated state**, and it does not by itself authorize writing 120 into `InventoryMovement.unit_cost` or into the original `JournalEntry.amount`. Those remain what they were at posting time, permanently. If an additive correction (Q1-b) is the chosen path once Q3's Correction Event is defined, the correction itself becomes a new fact, independently auditable — it does not overwrite the fact it corrects. Restated plainly: **Derived corrected state ≠ mutation of the original posted fact.** Any design that quietly rewrites a historical value to "fix" it violates this, regardless of how correct the new value is.

## Q3.6 — Schema Design Specification (entity boundaries, cardinalities, persisted-vs-derived — still no migration, no SQLAlchemy model)

### Q3.6-A — Entity Boundaries
- **`CorrectionEvent`** — the root entity. Item-scoped (per the audit's resolution of Item Scope). Holds identity, `trigger_type`, `scope_completeness` (belongs here, not per-candidate — see the cardinality note below), `status` (lifecycle), and `analysis_as_of`.
- **`RootCauseComponent`** — child of `CorrectionEvent`, 1..N. Represents either the single newly-inserted movement or, for the reversal+re-entry shape, two linked components (`component_type`: `NEW_MOVEMENT` / `REVERSAL` / `REPLACEMENT`).
- **`TieGroup`** — child of `CorrectionEvent`, 0..N (zero exactly when every relevant date in the scope is unambiguous — fully `KNOWN` chronology). Represents one set of same-`movement_date` movements whose order is not determinable from `movement_date` alone.
- **`OrderingAssumption`** — child of `TieGroup`, 1..N. One specific resolution of that tie-group's order, expressed via Q2.5's reduced (run-collapsed) representation, not a raw permutation.
- **`CandidateState`** — child of `CorrectionEvent`, 1..N (never zero — even a fully `KNOWN`-chronology event has exactly one candidate, the single definite recalculation; `N > 1` only when genuine ambiguity exists). References the specific combination of `OrderingAssumption`s (one per relevant `TieGroup`) that produced it, per Q3.3.7's "globally consistent" requirement.
- **`DeltaRecord`** — child of `CandidateState`, holding the primitive deltas established in Q3.3.4 (`Δquantity`, `Δinventory_value`) at whatever granularity Q3.3.4 established (movement-level for value, regime-segment-level for quantity) — not a full recalculated snapshot.
- **`ImpactScopeElement`** — child of `CorrectionEvent`, 1..N. One node in the Q2.6 graph, discriminated by kind (`MOVEMENT` / `DOCUMENT` / `ACCOUNTING_EFFECT`), referencing the live record it represents (never copying its values).
- **`ImpactScopeRelationship`** — the graph's edges (`causes` / `precedes` / `propagates_to` / `belongs_to` / `produces_accounting_effect`). Storage shape (explicit edge table vs. implicit predecessor-pointer per element) is **not decided here** — this remains exactly the storage-shape question Q2.6 already deferred; only the semantic need for it is confirmed.
- **`AccountingCorrection`** — **not a new parallel entity duplicating what a `JournalEntry` already captures.** A thin reference/link record connecting a `CorrectionEvent` (and the specific `DeltaRecord`s it covers) to the actual `JournalEntry` created through the existing Boundary (`post_immediate`) when something is posted. This follows the same restraint already applied throughout 3B-5 — no parallel accounting subsystem, reuse what exists.

### Q3.6-B — Relationships & Cardinalities (corrected from the initial sketch, with reasons)
```
CorrectionEvent
 ├── 1 Item                                          (not N — per Item Scope resolution)
 ├── 1..N RootCauseComponent                         (never shared across events — see note below)
 ├── 0..N TieGroup
 │     └── 1..N OrderingAssumption
 ├── 1..N CandidateState                             (corrected: 0..N → 1..N, see Q3.6-A)
 │     ├── 0..N OrderingAssumption (referenced)       (0 exactly when no TieGroup exists at all)
 │     └── 1..N DeltaRecord
 ├── 1..N ImpactScopeElement
 ├── 0..N ImpactScopeRelationship
 └── 0..N AccountingCorrection (reference)            (0 when Economic Effect exists with nothing posted — Q3.5.5)
```
**Two corrections to the original sketch, with justification:**
1. `CandidateState` is `1..N`, not `0..N` — an event with fully known chronology still has exactly one recalculated scenario; "candidate" does not imply "ambiguous," it implies "an analytically-derived result," and Q1's tiers apply to it regardless of whether `N = 1` or `N > 1`.
2. **`RootCauseComponent` is never shared across `CorrectionEvent`s, even for the multi-item-invoice case (scenario 6 below).** Each item's event gets its *own* `RootCauseComponent` record, independently referencing the same underlying document — not a many-to-many shared row. Sharing the row would mean withdrawing or re-analyzing one item's event could accidentally affect another's; independent ownership with a shared *document reference* avoids that coupling entirely.

### Q3.6-C — Persisted vs. Derived (extended from the six-row draft — two additions, with reasons)
| Category | Example | Persisted? | Why |
|---|---|---|---|
| Live-derived | current `average_cost` | **No** | Pure function of always-current data — "stale current data" is not a coherent concept |
| Analytical snapshot | `CandidateState` (+ `analysis_as_of`) | **Yes** | Frozen result of a specific past analysis run — re-deriving later can legitimately differ (that difference *is* Staleness) |
| Historical fact | `RootCauseComponent` | **Yes** | The triggering data change itself — not re-derivable from anything |
| Analytical provenance | `OrderingAssumption` | **Yes** | The specific choice that produced a given candidate — required for the candidate to be reviewable at all (Q3.3.3) |
| Derived relationship | `overlap_status` | **No** | Computable on demand from two events' `ImpactScopeElement` references — storing it risks stale derived metadata |
| Accounting result | posted `AccountingCorrection` reference | **Yes** | A decision that was executed — not reconstructable from current state alone |
| **Added — Impact Scope membership itself** | the set of `ImpactScopeElement` nodes | **Yes** | Must be a stored snapshot, not a live re-walk of the graph — Staleness (per the Q2.6 connection already established) is defined by comparing *new* data against this *stored* scope; a live-only scope would have nothing fixed to compare against |
| **Added — Correction Completeness state** | which `DeltaRecord`s have a linked `AccountingCorrection` | **Yes** | A decision/execution record (which subset was actually posted), not derivable from the economic analysis alone — this is exactly what Q3.5.6's reconciliation check needs to verify against |

### Final design test — twelve scenarios walked through the model above, not merely asserted to work
1. **Backdated purchase → one affected Sale.** `RootCauseComponent` = 1 (the purchase); `TieGroup` = 0 if dates don't collide; `CandidateState` = 1; `ImpactScopeElement` = {purchase, sale} + one edge. No special case.
2. **Backdated purchase → several Sales.** Same shape, larger `ImpactScopeElement`/edge set. No special case.
3. **Same root → several tie-groups → several Candidates.** `TieGroup` > 1, `CandidateState` count = the cross-product established in Q3.3.7 (can be large — a real *data volume* concern, not a *modeling* one; the schema shape does not break, it just has to hold more rows).
4. **Transfer chain W1→W2→W3.** `ImpactScopeElement` spans three warehouses' movement instances with `propagates_to` edges crossing warehouse labels — handled identically to Q2.6's own reachability demonstration.
5. **Transfer cycle W1→W2→W1.** Same graph model; cycles are fine because nodes are movement *instances*, never warehouse labels (Q2.7's termination-guarantee clarification applies unchanged) — already demonstrated computationally in Q2.6.
6. **Multi-item invoice → several Correction Events.** Handled by the Item Scope resolution: several independent `CorrectionEvent`s, each with its own `RootCauseComponent` referencing the same document (never a shared row, per Q3.6-B's correction).
7. **Candidate → root cause vanishes → WITHDRAWN.** A lifecycle status transition only; no entity-model change needed.
8. **Candidate analyzed → new data → STALE.** Enabled directly by the newly-added "Impact Scope membership is persisted" row above — staleness is a comparison between current data and the *stored* scope snapshot, not a live recomputation.
9. **Partial Scope.** `scope_completeness` lives on `CorrectionEvent`, not per-`CandidateState` — clarified here because all candidates of one event share the same underlying traversal/graph; only the tie-resolution differs between them, not the scope that was walked to find them.
10. **Complete Analysis + Partial Correction.** Naturally represented: only some `DeltaRecord`s end up with a linked `AccountingCorrection` reference; the rest remain economically identified but unposted — exactly Correction Completeness's job.
11. **Multiple Correction Events with overlapping Impact Scope.** Because `ImpactScopeElement` references live movement/document IDs rather than copies, overlap between two events is a plain set intersection on those referenced IDs — no stored `overlap_status`, no special case.
12. **Event with Economic Effect but no Accounting Correction.** `AccountingCorrection` reference count of zero is an entirely ordinary state (e.g., held at `PENDING`/`APPROVED` under Policy C for `ASSUMED` chronology) — not an edge case requiring special handling.

**Outcome: all twelve scenarios are representable without introducing a single special-case field.** The exercise surfaced two genuine cardinality corrections (`CandidateState` 1..N not 0..N; `RootCauseComponent` never shared across events) and two field-placement clarifications (`scope_completeness` at the Event level; Impact Scope membership itself belongs in the "persisted" column) — real refinements produced by testing the model against concrete cases, not just describing it in the abstract.

## Pre-Implementation Schema Audit (still no migration, no SQLAlchemy model — a readiness test, not implementation)
Grounded in the project's own existing conventions, confirmed by reading `models.py` directly rather than inventing generic patterns: integer autoincrement `id` primary keys throughout; a `source_type` (string) + `source_id` (nullable int, not a true FK) polymorphic-reference pattern already used by both `InventoryMovement` and `JournalEntry` for "this record's origin could be one of several document types"; named `ck_*` `CheckConstraint`s (e.g., `ck_settlement_amount_positive`); and — critically, exact precedent for one of this audit's own questions below — `Settlement.journal_entry_id` and `OpeningBalance` both already use `ForeignKey("journal_entries.id"), unique=True` for "this record owns exactly one independent JournalEntry."

**Entities, final names** (table names, snake_case, matching existing style):
`correction_events`, `correction_event_root_causes`, `correction_event_tie_groups`, `correction_event_ordering_assumptions`, `correction_event_candidate_states`, `correction_event_candidate_ordering_links` (junction), `correction_event_delta_records`, `correction_event_impact_scope_elements`, `correction_event_impact_scope_relationships`, `correction_event_accounting_corrections`.

**Primary keys.** All `id: Mapped[int] = mapped_column(primary_key=True)` — no deviation from the existing project-wide convention.

**Foreign keys — real, not generic.**
- `correction_events.item_id → items.id`, `NOT NULL` (Item Scope, Q3.6-A).
- `*.correction_event_id → correction_events.id` on every direct child table, `NOT NULL`.
- `correction_event_root_causes`: origin reference via the **existing** `source_type`/`source_id` pattern (not a true FK) — exactly how `InventoryMovement`/`JournalEntry` already reference their own polymorphic origins; reusing it here rather than inventing a parallel mechanism.
- `correction_event_ordering_assumptions.tie_group_id → correction_event_tie_groups.id`.
- `correction_event_candidate_ordering_links`: composite junction, `candidate_state_id → correction_event_candidate_states.id` + `ordering_assumption_id → correction_event_ordering_assumptions.id`, **plus a denormalized `tie_group_id`** carried onto the junction row itself (see the UNIQUE constraint below — this is why it's there, not redundancy for its own sake).
- `correction_event_delta_records.movement_id → inventory_movements.id` — a **true** FK here, unlike Root Cause/Impact Scope Elements, because a Delta Record is always specifically about a movement, never a document or an accounting effect — no polymorphism needed for this one table.
- `correction_event_impact_scope_elements`: origin reference via `source_type`/`source_id` again (can be a movement, a document, or an accounting effect — genuinely polymorphic, unlike Delta Record).
- `correction_event_impact_scope_relationships`: `from_element_id`/`to_element_id → correction_event_impact_scope_elements.id`, plus `relationship_type` (the five kinds from Q2.6/Q3.2).
- `correction_event_accounting_corrections.journal_entry_id → journal_entries.id`, **`unique=True`** — directly reusing the `Settlement`/`OpeningBalance` precedent found above, for exactly the same reason (one JournalEntry, one owner).

**UNIQUE constraints — one is a genuine DB-level invariant, not housekeeping.**
- `correction_event_impact_scope_elements`: `UNIQUE(correction_event_id, source_type, source_id)` — the same underlying movement/document cannot be added twice to one event's scope.
- `correction_event_accounting_corrections`: `UNIQUE(journal_entry_id)` — per the Settlement/OpeningBalance precedent; a JournalEntry belongs to at most one correction.
- **The load-bearing one**: `correction_event_candidate_ordering_links`: `UNIQUE(candidate_state_id, tie_group_id)` — enforced via the denormalized `tie_group_id` column mentioned above. This is not convenience — it is the database *mechanically preventing* a Candidate from referencing two different `OrderingAssumption`s for the *same* `TieGroup` simultaneously, which would directly violate Q3.3.7's "globally consistent" requirement. Without this constraint, an internally self-contradictory candidate becomes representable; with it, the database itself rejects that state, not just application code.

**CHECK constraints.** Most lifecycle/type constraints belong as `Enum` columns (`status`, `component_type`, `chronology_basis`, `scope_completeness`), matching the project's existing preference for `Enum` over raw string+CHECK (see `JournalEntryStatus`). No numeric-positivity CHECK is appropriate on `DeltaRecord` — unlike `Settlement.amount_foreign > 0`, deltas are legitimately signed (a decrease is a valid, expected value), so forcing positivity would be actively wrong here, not merely unnecessary.

**Indexes, tied to specific lookup needs — and one honest limitation.**
- `correction_events(item_id)`, `correction_events(status)` — event/item lookup and workflow queries (e.g., "all PENDING events").
- `correction_event_impact_scope_elements(source_type, source_id)` — this is the index overlap detection and root-cause lookup both actually run on: "which correction event(s) reference this specific movement/document."
- `correction_event_accounting_corrections(journal_entry_id)` — reverse lookup from a journal entry to its correction, if any (redundant with the UNIQUE constraint's own index in SQLite/most DBs, but named explicitly here since the lookup direction matters for query planning).
- **Honest limitation on staleness detection**: no index makes *graph reachability* itself fast — an index can quickly find "does this event's scope already reference this item/warehouse," but confirming a *new* movement falls within the specific reachable subgraph already recorded (Q2.6's own connection to staleness) is a graph-traversal question, not a single-index lookup. The index narrows the candidate set of events worth re-checking; it does not replace the reachability check itself.

**Append-only vs. updatable — one governing rule, stated plainly.** Every child table (`root_causes`, `tie_groups`, `ordering_assumptions`, `candidate_states`, `delta_records`, `impact_scope_elements`, `impact_scope_relationships`) is **append-only once created**, directly extending the "recalculation does not mutate historical facts" principle from a rule about `InventoryMovement`/`JournalEntry` to a rule about the Correction Event's own analytical history. A `STALE` re-analysis does not overwrite the old `CandidateState` rows — it creates **new** ones under a new `analysis_as_of`, leaving the old (now-superseded) analysis intact for audit purposes. On `correction_events` itself, exactly **one** field is mutable through the object's life: `status`. Everything else about the event (its item, its root causes) is fixed at creation.

**Preventing "one candidate becomes truth before approval," enforced structurally, not by convention.** No boolean or default flag sits on `CandidateState` implying preference. Instead, `correction_events` carries a single **nullable** `approved_candidate_state_id → correction_event_candidate_states.id`, set **only** at the moment of actual approval (the `PENDING → APPROVED` transition) and `NULL` throughout `CANDIDATE`/`ANALYSIS`/`PENDING`/`STALE`. While `NULL`, every `CandidateState` is equally "one analytical possibility" — nothing in the schema privileges any of them until that one explicit field is set by an explicit action.

**WITHDRAWN / STALE preserve audit trail without deletion — a direct consequence of the append-only rule above, not a separate mechanism.** `WITHDRAWN` and `STALE` are values of the single mutable `status` field; no row is ever deleted to represent either. A withdrawn Candidate's `RootCauseComponent`s remain exactly as recorded; a stale Pending event's superseded `CandidateState`s remain exactly as they were computed, simply no longer reachable from `approved_candidate_state_id` (which stays `NULL` until a *later*, fresh analysis produces new candidates and one is approved).

**Can the model prevent illogical states at the DB level, not just Python? — Answered honestly, both ways.** Some invariants genuinely are DB-enforceable and are proposed as such above: no duplicate scope element (UNIQUE), no self-contradictory candidate (the `tie_group_id` UNIQUE on the junction table), no orphaned correction-to-journal-entry link (UNIQUE + FK). Others remain application-level by necessity — e.g., "a `WITHDRAWN` event's `approved_candidate_state_id` must stay `NULL`" spans a status value and a separate column in a way a single-table CHECK cannot express portably, and would need to be enforced in the service layer, exactly as the project already does today for `JournalEntry.is_balanced()` (an application-level check, not a DB CHECK, despite being the system's single most important invariant). This is not a compromise specific to Correction Event — it matches the balance the existing codebase already strikes between DB-level and service-level enforcement.
