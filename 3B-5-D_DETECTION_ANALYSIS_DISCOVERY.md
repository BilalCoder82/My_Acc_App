## Cluster 1, Question 1 — What constitutes a Detection Candidate? (answered by tracing actual code, not proposed from scratch)

**Every call site that creates an `InventoryMovement` was traced, not assumed.** Nine construction sites exist across six files — `posting.py` (×2: sales, purchase), `returns.py` (×2: sales return, purchase return), `inventory_transfer.py` (×2: source OUT, destination IN), `invoice_cancel.py` (×1: reversal), `opening_balances.py` (×2: opening inventory, opening-inventory reversal). **No centralized "create movement" function exists today** — every one of these nine sites builds an `InventoryMovement(...)` directly. This is a real architectural fact, not a design preference, and it directly shapes what Cluster 1's next question (the lightweight hook) has to work with — flagged here because it surfaced while answering *this* question, not invented for it.

**What every one of the nine sites has in common, without exception:** each one has `item_id`, `warehouse_id`, and `movement_date` available at construction time, before or as the row is added to the session. This is the entire information surface Detection has to work with — nothing else is uniformly available across all nine sites (e.g., not every site has easy access to the same document-level context).

**Candidate definition, grounded in that common surface:**
> A newly-constructed `InventoryMovement` is a **Detection Candidate** if, at the moment of its creation, there exists at least one *already-committed* `InventoryMovement` for the same `(item_id, warehouse_id)` with `movement_date` later than the new movement's own `movement_date`.

This is a pure **existence check** on dates — it deliberately does **not** invoke anything from Q2.5's costing-order machinery (tie-group detection, ordering assumptions, or `id`-based tiebreaking). Detection only needs to know "does a later-dated movement already exist," not "what is the correct chronological order" — conflating the two would smuggle Q2.5's much harder problem into what should be a cheap, uniform pre-check. This distinction is worth stating explicitly because the two questions sound similar but are not: costing order matters only once full Analysis runs; detection only needs existence, not order.

**A finding worth flagging now, not deferred: this check requires no knowledge of `RootCauseComponentType`.** Tracing `invoice_cancel.py`'s reversal path specifically: its movement is dated at `cancel_date`, a caller-supplied parameter — **not hardcoded to "today."** Nothing in the code prevents `cancel_date` from itself being earlier than already-posted later movements. This means the *same* uniform existence check, applied without inspecting `source_type` at all, correctly catches both Root Cause shapes established in Q3.1 (`NEW_MOVEMENT` and `REVERSAL`/`REPLACEMENT`) — a reversal dated normally (at or after existing history) simply never trips the check; one backdated deliberately would, exactly like any other movement. Detection does not need to special-case which kind of Root Cause it might be looking at — this was not assumed, it was confirmed by reading `invoice_cancel.py`'s actual `cancel_date` handling.

**What remains genuinely open for Cluster 1's next question (the lightweight hook, item 2) — not this one:** the existence check above requires a query filtered by `(item_id, warehouse_id, movement_date)`, and `InventoryMovement` currently has **no index on any of those three columns** (confirmed by reading the model — only the primary key and the FK columns exist, neither `item_id` nor `warehouse_id` nor `movement_date` is declared with `index=True`). A "lightweight" hook running this check at every one of the nine call sites, on every ordinary posting, would not actually be lightweight without an index to support it. This is a real prerequisite the next question needs to address — not a decision to make now, and not evidence that reopens anything from Q1/Q2/Q3 (Q1 never specified an index; it specified a policy), but a concrete fact this tracing surfaced that Cluster 1's second question cannot responsibly skip.

## Cluster 1, Question 2 — The actual lightweight indexed hook (mechanism, query, index, transaction timing, coverage — no code written yet)

**Where to place it, given no central creation point exists (confirmed above) — this is the decision the "implementation convenience" caution applies to most directly.** Two options were weighed, not one assumed:
- *(Rejected as premature)* Introduce a new centralizing "create movement" function now, and route all nine sites through it. This is exactly the kind of move the governing principle warns about — it would make the hook trivial to add, but *convenience* is not evidence that this refactor is required, and it touches nine existing, already-characterized call sites for a reason unrelated to their own correctness.
- *(Selected, on a coverage argument, not a convenience one)* **A SQLAlchemy ORM-level event**, not per-site code. Every one of the nine sites, without exception, creates its row via `session.add(InventoryMovement(...))` — there is no raw-SQL insert path anywhere in this codebase for this table. A session-level event (`Session.after_flush`, confirmed available and appropriate for this SQLAlchemy version, 2.0.52) fires for *any* newly flushed `InventoryMovement` instance regardless of which service module created it — including a hypothetical tenth call site added by a future contributor who has never heard of Cluster 1. This is a **stronger coverage guarantee** than manually adding a call at each site, which could silently miss a new tenth site; that is an evidence-based argument for this choice, not a convenience-based one.

**Why `after_flush`, not `before_flush` or a mapper-level `after_insert`, specifically:** `after_flush` runs once SQL for all pending changes in this flush has been emitted to the database *within the current transaction* — meaning sibling rows inserted in the *same* flush (e.g., multiple lines of one multi-line invoice, all sharing that invoice's date) are already visible to a query at this point. A mapper-level `after_insert` event fires per-row *during* the flush itself, when session state is not safe for a new ORM query (a known SQLAlchemy constraint, would require dropping to the raw `Connection` and Core SQL instead of the ORM session) — session-level `after_flush` avoids that complexity for no loss of correctness here.

**The query, and the index it actually justifies (checked against the query shape, not assumed):**
```sql
SELECT 1 FROM inventory_movements
WHERE item_id = :item_id AND warehouse_id = :warehouse_id AND movement_date > :new_date
LIMIT 1
```
`item_id` and `warehouse_id` are equality predicates; `movement_date` is a range predicate. Standard B-tree index design puts equality columns first, the range column last: **`INDEX(item_id, warehouse_id, movement_date)`** — this column order is derived from this specific query, not a generic "index the FK columns" guess. The new row itself can never satisfy `movement_date > :new_date` against its own date, so no explicit self-exclusion is needed in the query.

**A real technical detail flagged for the eventual implementation, not resolved here:** if a Candidate is detected, writing a new `correction_events` row *during* the `after_flush` handler risks triggering a nested flush (a documented SQLAlchemy hazard when mutating the session from within a flush event). The safe pattern — noted here so it isn't rediscovered the hard way later — is either deferring the actual `CorrectionEvent` write to a subsequent `after_commit` event (once the triggering transaction is safely finished), or using the raw `Connection` for a Core-level insert inside `after_flush` rather than `session.add()`. Which of these two is preferable is an implementation decision for when this is actually coded, not a Discovery-phase decision. **A further, related question that must not be lost by the time this reaches implementation**: if the triggering post succeeds and commits, but Candidate creation itself then fails (relevant specifically under the `after_commit` option, where the original transaction is already done), what happens to that missed detection? Not resolved here — flagged so it survives into the design that actually gets built.

**Correction to a claim in the previous answer — `after_flush` visibility is not the same as `Q1`'s "already-committed" requirement, and this matters concretely.** `after_flush` makes *this transaction's own* pending writes visible to further queries *within that same transaction* — but they are not yet committed; a crash or rollback before commit would erase them. Q1's Detection Candidate definition specifically requires an *already-committed* later movement — sibling rows created in the *same* flush (e.g., two lines of one multi-item invoice posted together) are **not** "already-committed history" relative to each other; they are part of one atomic operation happening *now*, not a prior fact a new backdated entry could be correcting. The earlier claim that "the new row can never satisfy `movement_date > its own date`, so no exclusion is needed" is true only for a row excluding *itself* — it does **not** exclude *sibling* rows from the same flush, which is a real gap. **Fix**: the newly-flushed `InventoryMovement` instances for this transaction must be captured (via `before_flush`, from `session.new`, before they're cleared into persistent state) and explicitly excluded (`AND id NOT IN (...)`) from the existence-check query run in `after_flush` — otherwise two same-item lines on one invoice could spuriously flag each other as Detection Candidates purely because they happen to share a date and were flushed together.

**Four acceptance tests this hook design must satisfy once built (not run now — Discovery, not implementation):**
1. **Coverage** — post through each of the nine paths individually and confirm the hook fires for all nine, not a subset.
2. **Negative** — a newly-inserted movement with no later-dated sibling for its `(item_id, warehouse_id)` produces no Candidate.
3. **Same-flush** — multiple movements from one flush (e.g., a multi-line invoice) never treat each other as "pre-existing committed history," per the correction above.
4. **Reversal** — a genuinely backdated `cancel_date` triggers detection through the exact same mechanism as any other movement, with no `source_type`-specific branch anywhere in the hook.

## Cluster 2, Question 1 (item 4) — Building Impact Scope from real data (join keys traced, not invented)

**Every edge type Q2.6 requires already has a concrete, existing join key in the schema — none needed to be invented:**

- **`belongs_to` (movement → document)**: already a direct field on the movement itself — `InventoryMovement.source_type`/`source_id` point straight at the originating `Invoice`/`StockTransfer`/etc. No traversal needed; this edge is read off the row directly.
- **`propagates_to` — transfer edges (source warehouse → destination warehouse)**: traced in `inventory_transfer.py` — both the OUT movement (source) and the IN movement (destination) of one transfer are created with the *identical* `source_type="stock_transfer"` and `source_id=transfer.id`. This shared pair is the join key connecting the two sides of one transfer — confirmed in the actual code, the same evidentiary standard used throughout this phase.
- **`produces_accounting_effect` (movement → JournalEntry)**: **this one is not a direct field-to-field link — it is an indirect match through a shared origin.** Tracing `posting.py`: a sales invoice's movements are created with `source_type="sales_invoice", source_id=invoice.id`, and the *same invoice's* `post_immediate(...)` call creates its `JournalEntry` with — confirmed by reading `JournalEntry`'s own columns — the identical `source_type`/`source_id` pattern (`source_type: Mapped[str]`, `source_id: Mapped[int | None]`, both present on `JournalEntry` exactly as on `InventoryMovement`). **The accounting-effect edge is therefore: match `InventoryMovement.(source_type, source_id)` to `JournalEntry.(source_type, source_id)`** — not a new relationship to add, an existing pattern already shared by both tables for an unrelated original reason (their own document traceability), reusable here without modification.
- **`precedes`/temporal succession within one warehouse**: the same `(item_id, warehouse_id, movement_date)` ordering already established for `get_item_stock_summary()` since 3B-5-A/B — walking forward from a node means the next reachable node is the next movement for the same `(item_id, warehouse_id)` by `movement_date` (with Q2.5's tie-group machinery applying exactly where dates coincide, unchanged from its own design).

**Walk termination — no new decision, just confirming what Q2.3/Q2.7 already imply for the concrete algorithm:** because Q2.3 disproved any safe local stopping point, and Q2.7 deliberately left bounding as an undecided policy, the *unbounded* version of this walk — the one this Discovery phase is describing — does not stop early. It expands the frontier from the root cause across every edge type until no new node is reachable, which in practice means walking every touched warehouse's chronology forward to its own latest movement. Where a Q2.7 bound eventually gets decided, it is applied *on top of* this walk (producing `scope_completeness = PARTIAL` when it cuts the walk short) — it does not change what "complete" means here.

## Cluster 2, Question 2 (item 12) — Guaranteeing coverage of the whole Item Scope, not a fragment

The risk this question is really naming: an implementation that only follows *some* edge types at each node (e.g., a version that walks temporal succession correctly but forgets to check for an outgoing transfer at every node it visits, not just the root) would silently produce an *incomplete* graph while appearing to have "walked to the end." This is a real, specific implementation-correctness risk, not a hypothetical one — Q2.4's own cycle-test scenario is exactly the kind of case such a bug would miss (a transfer several hops downstream, not visible from the root cause alone).

**The discipline this requires, stated as a concrete rule for the eventual algorithm**: at *every* node visited during the walk — not only the root — all edge types must be checked (temporal successor in its own warehouse, any transfer the node participates in as source or destination, its owning document, its accounting effect if any), and every newly-discovered node must itself be checked the same way before the walk is considered finished. This is the same closure/reachability logic already demonstrated computationally in Q2.6's own exploration script (`build_graph`/`reachable_from`) — Cluster 2's job is confirming that *real* data supports building exactly that graph, which the join keys above establish; ensuring the *algorithm itself* checks every edge type at every node, not just the root, is an implementation-correctness discipline to carry into the eventual code and its own characterization tests (a graph-completeness test — comparable in spirit to the coverage test already specified for Cluster 1 — belongs here too, once this is actually built).

## Cluster 2, Question 3 — Node identity / runtime graph model (the schema already answers this; nothing new is being decided)

Six sub-questions, each answered by what Q2.6/Q3.6 already fixed, not by a new choice:

**Is each `InventoryMovement` its own node?** Yes — and it has to be, since the entire Q2.1–Q2.3 mathematical apparatus (state vector, Baseline vs. Recalculated comparison) operates per individual movement. This is the primary node type the recalculation walk (Cluster 3) will actually traverse and compute over; the other node types exist for reporting/review, not for the arithmetic itself.

**Is `JournalEntry` a node?** Yes, as the concrete referent of `ImpactScopeElementKind.ACCOUNTING_EFFECT` — already a distinct value in that enum since Q3.6-A, not a new addition now. It represents the whole `JournalEntry`, not an individual `JournalLine` within it — consistent with `CorrectionEventAccountingCorrection.journal_entry_id` already being entry-level, not line-level, in the schema built in 3B-5-C.

**Is the source Document a node?** Yes — `ImpactScopeElementKind.DOCUMENT`, already distinct from both `MOVEMENT` and `ACCOUNTING_EFFECT` in the same enum. Kept as its own node rather than folded into the movement, specifically so the rare same-item-duplicate-line case (Finding C's territory, kept out of this design track) doesn't force special-casing later — a document can in principle relate to more than one movement of the same item without breaking the model, even though that's not the normal case.

**Is Accounting Effect a separate node, or a projection of `JournalEntry`?** A separate node corresponding **exactly 1:1** to a real `JournalEntry` row — not a further abstraction layered on top of it, and not the same node as the Document. Concretely: for a sales invoice, the Document node *is* the `Invoice` row, and the Accounting Effect node *is* the `JournalEntry` row created for it via `post_immediate` — two different tables, two different rows, linked to each other and to the Movement node only through the shared `(source_type, source_id)` identity traced in Question 1, not through a hierarchy where one contains or derives the other.

**Transfer OUT/IN — two linked nodes, or one "transfer node"?** **Two separate `MOVEMENT` nodes**, connected by one `propagates_to` `ImpactScopeRelationship` edge — never collapsed into a single node. This is not a stylistic choice: the OUT movement and the IN movement each carry their *own* independent state vector (their own warehouse's `quantity`/`inventory_value`, per Q2.1), and Cluster 3's recalculation walk needs to compute Baseline vs. Recalculated separately for each side. Collapsing them into one node would silently erase exactly the distinction Q2.4's D-Lemma 3 was built on (source-side vs. destination-side effects behaving differently). This also requires no schema change — `ImpactScopeElement` is already one row per node and `ImpactScopeRelationship` already connects two separate element rows, so the two-node model is simply what the existing schema does, not an extension of it.

**How does a `RootCauseComponent` (possibly a reversal+replacement pair) map onto this graph?** `RootCauseComponent` and `ImpactScopeElement` are not mutually exclusive, and not the same table for a reason — `RootCauseComponent` (Q3.1/3.2) records *why* the event exists and which component(s) triggered it; `ImpactScopeElement` (Q2.6) records the graph itself. **The root cause's own movement(s) are themselves also ordinary `ImpactScopeElement` nodes** — specifically, the seed(s) the traversal walk starts from. For the single-movement shape, there is one seed. For the reversal+replacement shape, **both** components get their own `ImpactScopeElement` node (the reversal is itself a real `InventoryMovement`/`JournalEntry` pair, created by `invoice_cancel.py`, exactly like any other movement) — the walk starts from *both* simultaneously, and they are expected to converge into one connected graph precisely because they correct the same underlying economic fact and therefore share downstream reachability. No special-case handling is needed for this shape beyond starting the walk from two seeds instead of one.

**Cluster 2 status: now closed.** All three questions (edge sourcing, closure discipline, node identity) answered from existing schema and code, nothing invented, nothing reopened from Q2/Q3.

## Cluster 3, Question 1 — Recalculation mechanics, using `accumulate_average_cost()`'s *actual* semantics, not an idealized version of it

**The literal behavior just re-confirmed is the crux of this entire question.** `accumulate_average_cost()`, exactly as it exists since 3B-5-B, does one specific thing for OUT movements: it uses `m.unit_cost` **from whatever `MovementFact` it is handed** — it never re-derives that cost from the running total, regardless of caller or context. This single fact splits Baseline and Candidate into two genuinely different *procedures*, not two calls with different inputs to the same procedure:

**Baseline — the function is used exactly as-is, unmodified, called once.** Baseline's `MovementFact` list is built directly from the *stored*, immutable `InventoryMovement` rows — `unit_cost` for every IN **and every OUT** comes straight from the database, because that is precisely what "historical fact" (Q2.1's own language) means: the value that was actually posted. A single batch call to `accumulate_average_cost(baseline_facts)` reproduces exactly what `get_item_stock_summary()` already computes today — this is not new work, it is calling the existing, already-characterized primitive with no modification whatsoever.

**Candidate — cannot be one batch call with a pre-built list, because OUT's cost must be *re-derived*, and the function itself will never do that.** If the Candidate's `MovementFact` list were built the same way as Baseline's (stored `unit_cost` values copied onto every fact) and handed to `accumulate_average_cost()` once, the result would be *identical* to Baseline — nothing would actually be recalculated, because the function trusts whatever `unit_cost` it's given for OUT, and copying the stored value gives it exactly the old answer. **The walk has to be incremental**: process movements one at a time in the Candidate's chronological order (per its specific `OrderingAssumption` for any tie-group it touches); for each **IN**, its cost is an external, already-known fact (a purchase's own recorded cost — never derived, per Q3.3.4) and gets appended directly; for each **OUT**, its cost for *this* candidate must first be read off the *current running average of the facts accumulated so far in this candidate's own sequence* — i.e., call `accumulate_average_cost()` on the prefix built up to that point, take its `average_cost`, use that as this OUT's `unit_cost` in the new `MovementFact`, *then* append it and continue. This reuses the existing primitive's exact math at every step — nothing about its internals changes — it is simply invoked repeatedly over a growing prefix instead of once over a finished list.

**This directly answers "what does it mean that OUT.unit_cost is a historical fact" for the Candidate side, precisely:** the stored `InventoryMovement.unit_cost` is never read, touched, or overwritten during the Candidate walk for a re-derived OUT — a *new*, separate value is computed in memory (destined for `DeltaRecord.delta_inventory_value`'s underlying comparison, per Q3.3) and the database row is never written to. "Historical fact, not rewritten" is satisfied by construction: the walk produces a comparison value, not a mutation.

**Efficiency note, not a semantics change:** literally calling the O(n) `accumulate_average_cost()` from scratch on every growing prefix would be O(n²) over a long chain. The corrected implementation should maintain the same two running accumulators (`total_qty`, `total_cost`) directly rather than re-summing a list each step — this is *behaviorally identical* to repeated prefix calls (same formula, same result, verified against the existing function's own math) and is an implementation-efficiency detail, not a change to what's being computed.

**Multiple warehouses and Transfer OUT/IN — a genuine algorithmic dependency, not two independent walks.** Per Cluster 2, each `(item_id, warehouse_id)` has its own accumulator state. A Transfer's OUT is processed within its *source* warehouse's own running walk, exactly like an ordinary OUT (re-derived from that warehouse's current running average, same as any other OUT). Its IN is processed within the *destination* warehouse's walk — but its cost **is** the source OUT's just-computed cost, which means **the destination's IN cannot be processed before the source's OUT has been**. This is not two parallel per-warehouse walks that happen to touch each other — it is one walk over the whole reachable graph (Cluster 2), where a `propagates_to` edge is a real *processing-order dependency*, not just a reporting link: the algorithm must visit nodes in an order that respects both each warehouse's own chronology *and* every transfer's OUT-before-IN dependency simultaneously (a topological constraint layered on top of the per-warehouse chronological one).

**Multiple candidate orderings — no new mechanism, just repeating the same walk once per candidate.** Each `CandidateState` (Q3.3.7's globally-consistent combination of `OrderingAssumption`s) determines one specific total order for the movements in its scope; the incremental walk described above runs once per candidate, over that candidate's own order, producing that candidate's own `DeltaRecord`s. The Cartesian explosion already established in Q3.3.7 is a cost concern for *how many times* this walk runs, not a change to how any single run works.

**Baseline without a root cause / Candidate with one — clarifying what's actually being compared.** "Baseline" is not "the state before this item existed" — it is simply what `accumulate_average_cost()` already computes today from the *currently stored* movements (which do **not** yet include a not-yet-approved correction, by definition, since nothing gets written until Q1's later tiers). "Candidate" is the same computation with the Root Cause's own component(s) (Q3.1) included in the walk at their true chronological position. The comparison Q2.2 defined (`Affected(M)`) is between these two walks' results at each node — nothing here changes that definition, this section only establishes *how* each side of it is actually computed.

## Cluster 3, Question 2 — Runtime representation of Baseline vs. Candidate state (working memory, not schema — Q3.6 already fixed what gets persisted)

**First clarification this question exposes: Baseline needs its own incremental walk too — not just one final summary.** Q2.2's `Affected(M)` test compares Baseline and Candidate *at each movement node*, not just their final totals. Because Baseline's OUT cost is always the stored fact (never re-derived, confirmed in Question 1), it doesn't need Candidate's re-derivation step — but it still needs to be walked movement-by-movement, in the item's actual stored order, to produce a **checkpoint** (running quantity + value) after every movement in scope. This checkpoint set is computed **once per analysis run** — it does not vary by candidate, since Baseline is the same regardless of which `OrderingAssumption` combination a given candidate resolves to.

**The runtime structures, extending an existing precedent rather than inventing a new one:**
- **`WalkAccumulator`** — a plain, non-ORM dataclass (`quantity: Decimal`, `value: Decimal`), one instance per warehouse touched during a walk (the item is fixed for the whole event, per the Item Scope resolution — only `warehouse_id` varies). This mirrors `accumulate_average_cost()`'s own two internal running totals (`total_qty`, `total_cost`) — nothing new is being modeled, just named and given a place to live across steps instead of living only inside that function's local scope.
- **`checkpoint` map** — `{movement_id → WalkAccumulator snapshot}`, captured immediately after each movement is processed. One such map for Baseline (computed once), and one per Candidate (computed once per candidate, in that candidate's own order).
- **Both extend the same pattern `MovementFact` already established in 3B-5-B** — a plain `@dataclass(frozen=True)`, no SQLAlchemy mapping, no session attachment. This is not a new design choice; it is applying 3B-5-B's own precedent (pure calculation state stays plain data, decoupled from persistence) to this walk's working state as well.

**The boundary that keeps working state from leaking into ORM/session state, stated as a one-directional rule:** the walk reads from ORM objects exactly once, at the start, to build its initial `MovementFact` list (a snapshot read) — from that point on, every accumulator, every checkpoint, every intermediate candidate state lives entirely in plain dataclasses that are never `session.add()`-ed and never touched by autoflush or dirty-tracking. Only **after** a walk finishes — once its final checkpoints are known — does the code construct the actual `CandidateState`/`DeltaRecord` ORM rows (Q3.6's schema) from those checkpoints and add them to the session. Transient simulation state flows in one direction into persisted rows; nothing ever flows back the other way, and nothing in between is ORM-tracked.

**What actually gets persisted vs. discarded, connecting back to Q3.3's own "only diffs matter" principle:** the walk naturally produces a checkpoint for *every* movement in scope (it has to, since it processes them in sequence), but only movements where `Affected(M)` holds (Baseline checkpoint ≠ Candidate checkpoint, per Q2.2) get an actual `DeltaRecord` row written. Checkpoints for unaffected movements are working memory only — computed because the walk passed through them, discarded once the comparison is done, never persisted. This keeps storage aligned with what Q3.3.4 already decided should be kept (primitive deltas only, not full snapshots) without needing a separate filtering pass — the filter is simply "did this checkpoint differ from Baseline's."

**Explicitly not resolved here, and not premature to leave open:** the actual traversal/scheduling algorithm — how the walk visits nodes in an order that respects both per-warehouse chronology and the Transfer OUT-before-IN dependency established in Question 1 (a real topological-ordering problem, not yet designed) — remains open, per your own instruction not to invent it before this runtime-representation question was settled.

## Cluster 3, Question 3 — Traversal / Scheduling Algorithm (checked for a hidden unproven assumption before writing anything down as settled)

**First, a finding that changes the shape of this question entirely: the scheduling problem only exists for Candidate walks — Baseline does not need it.** Re-reading `inventory_transfer.py` line-by-line: the destination `IN` row's `unit_cost` is set from **the exact same already-computed value** as the source `OUT` row's `unit_cost` — both are written from one variable, at one point in time, directly onto both rows. This means a transfer's destination `IN` cost is, for Baseline purposes, a plain stored fact exactly like any other `IN` — Baseline never needs to "compute" it from a source warehouse's state, because it simply *reads* what's already there, the same as it does for every other movement. **Baseline can therefore be computed as N independent, per-warehouse linear walks** (each warehouse in its own `movement_date` order, exactly matching today's `get_item_stock_summary()` behavior) — no graph-wide scheduling machinery is needed for it at all. The cross-warehouse dependency established in Question 1 (source `OUT` must be computed before dependent destination `IN`) is real, but it is **specific to Candidate's re-derivation step** — Candidate needs to know what the transfer cost *should have been* under the corrected chronology, which genuinely depends on the source warehouse's re-derived state at that point; Baseline has no such need because it never re-derives anything.

**Second finding: once a Candidate's `OrderingAssumption`s are applied, the "scheduling algorithm" has no real choices left to make.** A tie-group's `OrderingAssumption` doesn't leave the scheduler free to pick *an* order — it *is* a fully specified order for every movement in that tie-group, for this candidate. Combined with ordinary chronological edges (within each warehouse) and transfer dependency edges (source `OUT` before destination `IN`), a Candidate's full edge set leaves no ambiguity anywhere in its own Impact Scope. **The correct algorithm is therefore a plain topological sort of this fully-determined edge set** — not a "clever" scheduling heuristic, just linearizing an already-fixed partial order into a single sequence the incremental walk (Question 2) can process one movement at a time.

**Why a topological sort is guaranteed to exist — grounded in Q2.7's own termination-guarantee finding, not a new claim:** Q2.7 already established that the *movement-instance* graph is always a finite DAG, even though the *warehouse-label* graph can contain cycles (W1→W2→W1) — because each node is a distinct historical event that happened once, and every edge (chronological or transfer) only ever points from an earlier real event to a later one. A finite DAG always has at least one valid topological order. This was proven once, for a different purpose (termination), and is being reused here rather than re-argued.

**The one part of this not proven — flagged explicitly, per your caution against a hidden unproven assumption, not asserted as settled:** this reasoning assumes that a *valid* Candidate (one satisfying Q3.3.7's "globally consistent" requirement) can never produce a combined edge set that contradicts itself (e.g., simultaneously requiring movement A before B *and* B before A from two different constraint sources — a tie-group resolution conflicting with a transfer or chronological edge). No case where this happens was found or constructed, but it was not proven impossible either. **The honest position is: expected to hold, not verified to hold.** The concrete consequence for the eventual implementation: before trusting a topological sort's output, the algorithm should explicitly check the combined edge set for a cycle and treat that as a sign the candidate itself was malformed (a bug in candidate generation, not a valid state to silently process) — not assume a well-formed candidate guarantees an acyclic schedule without checking.

**Summary of what Cluster 3 has now established, stated together since the three questions turned out to be tightly linked:**
- Baseline: N independent per-warehouse linear walks, no scheduling needed, computed once per analysis.
- Candidate: one topological sort per candidate over its own fully-resolved edge set (chronological + transfer + tie-group), then one incremental walk (Question 2's mechanism) over that order.
- The scheduling "problem" essentially dissolves once `OrderingAssumption`s are treated as constraints rather than choices — what remains is mechanical linearization, with one explicit, flagged assumption (acyclicity of a valid candidate's edges) that the eventual code must verify rather than trust.

## Cluster 4 — Ambiguity in practice: Cartesian candidate generation, kept strictly separate from consistency-checking, execution, and comparison

**Four phases, deliberately not fused, per your own instruction** — mixing them is exactly how an invalid candidate could slip through and get silently "executed" with some ad-hoc fallback instead of being cleanly rejected:

1. **Generation** — produce the raw candidate space.
2. **Consistency check** — cycle-detect each raw candidate's combined edge set (Cluster 3's flagged, unproven-but-required check) *before* anything is executed.
3. **Execution** — only consistency-checked candidates run the incremental walk (Cluster 3, Questions 2–3).
4. **Comparison** — each executed candidate's checkpoints are compared against the one shared Baseline (computed once, per Cluster 3) to produce `DeltaRecord`s.

**Phase 1, refined by a direct application of Q2.5's own proven math — not every tie-group contributes to the explosion.** Q2.5 already proved that a tie-group consisting entirely of same-type movements (a pure IN-IN or pure OUT-OUT run) commutes fully — order provably does not matter for it. Such a tie-group should be represented with **exactly one** `OrderingAssumption` (there is nothing to choose between), contributing a factor of 1 to the Cartesian product — not multiple assumptions inflating candidate count for a distinction that provably makes no difference. **Only genuinely order-sensitive tie-groups** (containing at least one IN adjacent to an OUT, where Q2.5's disproof of naive commutativity actually applies) should ever have more than one `OrderingAssumption` generated in the first place. This means Phase 1 must *classify* each tie-group (order-insensitive vs. order-sensitive) before deciding how many assumptions to generate for it — this is not a new policy, it is reusing Q2.5's own proof to keep the product space as small as the mathematics actually requires, rather than uniformly generating alternatives for tie-groups that don't need them.

**The raw candidate count is knowable *before* Phase 2 or Phase 3 ever runs** — it is simply the product of each order-sensitive tie-group's assumption count (the count itself, not the candidates, is cheap to compute once tie-groups are identified in Cluster 2's walk). This is the concrete mechanism behind Q2.7's "human-in-the-loop scope confirmation" option: the system can know and surface "this analysis has *N* tie-groups, producing *M* candidates" before committing to generating, checking, or executing any of them — without this Discovery phase deciding *what* happens with that number (refuse, warn, proceed) — that remains Q2.7/Q5's threshold decision, deliberately still open.

**Generation should be lazy, not eager, specifically because of the phase separation above.** Because Phase 1 is cleanly separated from Phase 3, nothing forces the system to materialize and execute every candidate in the product space at once — a generator that yields one raw candidate at a time (checked in Phase 2, executed in Phase 3, one at a time) keeps the door open for whatever bounding policy Q2.7/Q5 eventually adopts (a cap on candidates checked, an early-exit once a size threshold is crossed, or unbounded execution) without this phase committing to any of those choices now. Cheap-to-compute total count (above) plus lazy generation together mean the size question can be *answered* before Q2.7/Q5 decide *what to do* with the answer.

**What Cluster 4 does not decide, on purpose:** no threshold for "too many candidates," no policy for what happens when Phase 2 rejects a candidate as cyclic beyond "it is not executed" (whether that's logged, surfaced to the accountant, or silently excluded from the candidate set the accountant reviews is a Q1/Q3 UX question, not a Cluster 4 one), and no decision about whether Phase 3's execution should run sequentially or be parallelized (a pure performance question, deferred to Cluster 7 per the original ordering).

## Cluster 5 — Completeness & Staleness in practice

**Item 9 — When is analysis `COMPLETE` vs. `PARTIAL`, concretely?** Given Cluster 2's closure walk (expand the frontier across every edge type until nothing new is reachable) and Q2.7's established fact that no bound exists today, the definition is entirely mechanical, not a separate computation: **`COMPLETE`** means the closure loop exited because the frontier became empty on its own — every reachable node, via every edge type, was actually visited. **`PARTIAL`** means the loop was stopped by an external bound before the frontier emptied naturally — whatever that bound eventually turns out to be (Q2.7/Q5, still undecided). This requires no new logic: it is simply recording *which of the two ways* the closure loop's own termination happened, using a fact the walk already knows about itself.

**A third dimension, surfaced here and not previously named — not to be confused with `scope_completeness`.** Cluster 4 established that Impact Scope discovery (Cluster 2) and candidate generation/execution (Cluster 4) are separate concerns. This means a scope can be fully `COMPLETE` (graph discovery reached every reachable node) while **candidate execution** is itself only partially done — e.g., a future policy caps how many of `M_raw` valid, non-cyclic candidates actually get executed (Phase 3) in one pass. This is a genuinely distinct kind of incompleteness from `scope_completeness` — call it **Candidate Coverage** for now (naming not finalized) — and it is also distinct from **Correction Completeness** (Q3.4/3.5.6: of what was *analyzed and approved*, how much was actually *posted*). **Three completeness-adjacent dimensions now exist, not two, and none may substitute for another:**
- `scope_completeness` — did graph discovery reach full closure? (Cluster 2/Q2.7)
- Candidate Coverage — were all mathematically valid candidates actually executed? (new, surfaced here, Cluster 4/5)
- Correction Completeness — of what was approved, how much was actually posted? (Q3.4/3.5.6)
This is flagged as a finding for the eventual `CorrectionEvent` design to account for explicitly, not resolved or named finally here — consistent with how Correction Completeness itself was surfaced mid-design in Q3.4 rather than anticipated from the start.

**Item 10 — When does a `PENDING` Candidate become `STALE`, concretely?** The mechanism does not need to be invented separately from Cluster 1's detection hook — it is the **same** `after_flush` event, running **one additional check**, using the **same** `(item_id, warehouse_id, movement_date)` index already justified in Cluster 1. Detection's question was "does a later-dated movement already exist anywhere in history." Staleness's question is narrower and different: **"does this newly-flushed movement share `(item_id, warehouse_id)` with a `MOVEMENT`-kind `ImpactScopeElement` already recorded for some `PENDING`/`ANALYSIS`-status `CorrectionEvent`, at a `movement_date` that falls within (or before the end of) that event's already-walked range for that warehouse?"** If so, that event transitions to `STALE`.

**Why this scoped check is sufficient, not just cheap — including the cross-warehouse expansion case.** A concern worth addressing directly: could a brand-new movement in a warehouse the recorded scope has *never* touched invalidate that scope without tripping this check? Only if it's connected to the existing scope via a *new* transfer — but a transfer is itself two movement insertions, and the transfer's own leg in the *already-touched* warehouse (the one already in the recorded scope) would itself satisfy the check above and correctly trigger `STALE`. The previously-untouched warehouse only enters the picture *after* re-analysis runs and the walk (Cluster 2) discovers it — which is exactly what re-analysis is for. The scoped check does not need to anticipate graph expansion in advance; it only needs to catch entry points into the *already-recorded* scope, and every entry point is, by construction, a movement in a warehouse already part of that scope.

**Explicit confirmation, per your instruction: none of `chronology_basis`, `scope_completeness`, or Candidate Coverage may substitute for another.** A `KNOWN`-chronology, `COMPLETE`-scope analysis can still have incomplete Candidate Coverage if execution was capped; a fully-covered set of candidates says nothing about whether the scope itself was walked to closure; and neither says anything about whether the ordering within any tie-group was actually determinable from data (`chronology_basis`). All three remain independently necessary, exactly as `scope_completeness` and `chronology_basis` were already kept independent since Q2.7/Q3.

## Cluster 6-A — Effect separation, stated mechanically against the actual schema

Three tables, three lifecycle stages, confirmed against the schema built in 3B-5-C — not three synonyms for "affected":
- **`ImpactScopeElement`** — membership in the discovered graph (Cluster 2's closure walk). A fact about reachability, nothing about economic magnitude or accounting treatment.
- **`DeltaRecord`** — a computed economic difference, for one specific `CandidateState`, at one specific movement, filtered to `Affected(M)` only (Q2.2). Still hypothetical — no posting has happened.
- **`CorrectionEventAccountingCorrection`** — a reference to an *actually posted* `JournalEntry`, created only once Q1's tier progression reaches `ACCOUNTING_CORRECTION` for whatever was approved.

**A genuine gap surfaced by checking this mechanically, not just conceptually:** re-examining the 3B-5-C schema, `CorrectionEventAccountingCorrection` carries only `correction_event_id` and `journal_entry_id` — **it has no explicit link to which specific `DeltaRecord`(s) it corrects.** This matters concretely: Q3.5.6's reconciliation check (`Σ posted = Σ analyzed for the corrected subset`) needs to know *which* deltas a given posted correction actually covers, and the current schema can only answer that at the whole-`CorrectionEvent` level, not the delta level. This is not evidence that Q3.6 was wrong — the schema audit's own twelve-scenario test never specifically exercised partial-correction-with-explicit-delta-attribution — but it is a real, concrete gap the eventual implementation needs a junction (`DeltaRecord` ↔ `AccountingCorrection`, likely many-to-many for a correction spanning several deltas) to close. Flagged here per the governing principle: this is *evidence*, surfaced by checking the schema against a requirement it needs to satisfy, not implementation convenience — it may be worth a small, additive schema change later, not a reopening of Q3.6's design.

## Cluster 6-B — Approval boundaries

**One gate, not several — mechanically confirmed.** Regardless of which confidence dimension governs whether a given candidate needs human sign-off, there is exactly one mechanism through which any candidate becomes eligible to proceed toward `ACCOUNTING_CORRECTION`: setting `correction_events.approved_candidate_state_id` (Q3.6-A's own design — `NULL` by default, no candidate privileged before this explicit action). Cluster 6-B does not need to invent a second mechanism for "automatic" cases versus "requires approval" cases — the same field serves both; what differs is only *whether an automated process or a human sets it*, which is a policy question, not an architectural one.

**What is explicitly known to gate that decision today, without deciding the gating policy itself:** three dimensions now established across this design track, each independently capable of restricting a candidate to manual approval — `chronology_basis = ASSUMED` (decided, Q1 Policy C), `scope_completeness = PARTIAL` (strong argument surfaced in Q3.4, not yet formally adopted as a rule), and incomplete Candidate Coverage (surfaced in Cluster 5, not yet evaluated as a gating factor at all). **This cluster does not decide how these three combine into one final policy** — only that they are the known inputs to whatever that policy turns out to be, and that a single approval mechanism can accommodate all three without needing per-dimension special-casing.

**What stays out of execution entirely, not merely "unapproved":** a candidate rejected by Cluster 4's consistency check (cyclic edges) never becomes eligible for approval at all — it is not a valid economic scenario, not a cautious one awaiting sign-off. Its `DeltaRecord`s are never created in the first place (Phase 3/Execution never runs for it), so there is nothing pending for it to approve or reject.

## Cluster 6-C — Performance, without letting it touch correctness

**The full pipeline, walked once to find where cost actually accumulates:** `Detection (Cluster 1) → Scope expansion (Cluster 2) → Candidate generation (Cluster 4) → Consistency check (Cluster 4) → Execution (Cluster 3) → Comparison (Cluster 3/4)`.
- **Detection**: O(1) per posting, given the index justified in Cluster 1 — does not grow with history size.
- **Scope expansion**: cost scales with the size of the *reachable subgraph* — already the entire subject of Q2.7's bounding discussion; nothing new here.
- **Candidate generation**: cheap by itself (lazy, Cluster 4) — but the *count* it will eventually enumerate is the product of sensitive tie-groups' assumption counts (Q3.3.7).
- **Consistency check, Execution, and Comparison**: each runs **once per candidate**, over the **whole scope** that candidate touches.

**The single most important finding of this cluster: total realistic cost is not scope size plus candidate count — it is their product.** Every candidate requires its own full walk over the (possibly large) scope; Q2.7's scope-size concern and Q3.3.7's candidate-count concern were established independently but **multiply** in the actual pipeline, not add. A correction that looks only moderately expensive on either dimension alone could become severe if both are simultaneously non-trivial — a large scope with several independent sensitive tie-groups. **This does not overturn the existing P95/2.0s and ≥50,000-row benchmark triggers (Q2.7/Q7)** — it sharpens what "realistic workload" has to mean for that benchmark: a scenario combining nontrivial scope size *and* multiple sensitive tie-groups simultaneously, not either dimension tested in isolation. This is a refinement of Q7's already-decided requirement ("realistic movement distribution"), not a new policy.

**The one guardrail this cluster insists on, stated explicitly so it survives into implementation:** any future performance optimization — pruning, caching partial walks, early-exiting comparisons — must be provably equivalent to the naive algorithm's result, not merely faster. Nothing about improving performance is licensed to change which movements are found `Affected`, which candidates are generated, or what any `DeltaRecord` contains. This restates, at the implementation-guardrail level, the same principle that has governed this entire phase: correctness determines scope and content; performance determines only execution strategy.
